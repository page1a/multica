# ADR-0003: 路由派票的执行席归属与来源可见性

- status: accepted
- date: 2026-10-03

## 背景

自动路由需要在执行席已有持有者时保持条件写入，否则一次状态变化就可能把正在工作的票改派给另一个智能体。此前智能体在票进入 `in_progress` 或 `in_review` 后仍可能直接改写执行席，服务端内部的验收交棒和额度接力也必须继续能够完成。与此同时，任务动态只显示“自动选派”而不说明来源，读者无法判断这次选择来自人的原话、人工设置还是路由判断。

## 决策

1. **执行席由服务端保护。** 路由开启时，`todo` / `backlog` 上智能体直接写入的智能体或小队执行人交给路由从零判断；票过了 `todo` 后，智能体不能把执行席换成不同的智能体或小队。重写同一执行人、指派给成员、经服务端核验的 `--per-quote` 原话、人工指派，以及新建票不受这条拦截影响。
2. **服务端流程保留内部改派能力。** 验收交棒、额度接力、审核交棒和 `issue handoff` 等由服务端执行的流程不经过智能体改派拦截；需要换人的智能体通过 `issue escalate`、关闭为 `blocked` 让路由建议，或提供可核验的 `--per-quote` 原话。
3. **自动选择必须说明来源。** 每条写入执行席的自动选派评论以「为什么是他」开头，并从共享常量取得 `原话`、`人工`、`档位`、`兜底` 四个来源标签。聊天智能体默认负责派票，执行席负责人负责推进和收口，不自行把票改给别人。

## 理由

- 让执行中的票保持稳定，避免智能体在自己运行期间绕过路由和用户意图重写负责人。
- 把服务端内部交棒与智能体请求分开，既封住漏洞，也不阻断验收和额度接力。
- 来源标签让任务动态可以解释谁决定了执行席，并为后续“接着做”“负载”等路由规则提供同一个可扩展边界。

## 后果

- 路由、CLI 和界面必须把被拒的智能体改派解释为服务端保护，并展示可用的替代路径。
- 新的自动选人规则要复用来源常量和评论格式，同时补齐服务端、Web/Desktop、CLI 三面契约及测试。
- 来源标签是跨界面协议；新增来源时要同步更新词汇表、路由技能说明和相关证据，不在单个入口另造字符串。
