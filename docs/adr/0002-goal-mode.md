# ADR-0002: 目标任务的完成线与服务端续跑

- status: accepted
- date: 2026-10-01

## 背景

Goal 模式需要让一张任务持续推进到明确的完成标准，同时在预算、无进展和席位额度问题出现时可见地停下。若把完成判断和续跑状态留在某个智能体会话里，换会话或换人后就无法可靠接续；若各入口各自实现，又会让服务端、界面和 CLI 的状态分叉。

## 决策

把 Goal 定义为“任务 + 一条完成线”。完成线由可核验检查项组成，在人确认后锁定，执行人不能改动；检查项全部通过后交给验收席，而不是由执行人自评完成。

目标状态、当前轮次、检查证据、下一步和 token / 运行次数 / 总时长预算由服务端持有。每轮结束时服务端根据检查项决定自动续跑、交给验收席或暂停。预算到 80% 提示；预算耗尽或连续多轮没有新进展时暂停，并复用统一带选项提问询问下一步。若单个席位额度确实耗尽，先换同档位、同方向的智能体接力；所有可用席位都耗尽时等待额度窗口恢复。

目标从四个既有入口进入同一个服务端开启动作；Web/Desktop 任务详情、`multica goal` CLI 和动态记录共享同一接口与状态。

## 理由

- 服务端持有锁定和续跑判定，避免提示词或单次会话绕过完成线、预算和验收边界。
- 任务记录携带最少接力信息，智能体更换、上下文压缩或进程重启后仍能继续。
- 统一入口和共享 API 让界面与 CLI 能显示同一进度、证据、预算和暂停原因。
- 区分目标预算与席位额度，避免一个智能体没额度时错误地终止仍有预算的目标。

## 后果

- 新的目标入口必须调用同一个服务端开启动作；不得在 Web/Desktop 或 CLI 另建目标状态。
- 新增完成判断只能补充可核验检查项和证据，不能让执行人直接宣布目标达成。
- 续跑、刹车、接力相关改动需要同时检查服务端、Web/Desktop、CLI 和平台技能文档的契约。
