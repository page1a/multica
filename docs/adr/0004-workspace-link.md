# ADR-0004: 跨工作区只读连通走单一出口，不复用访客

- status: accepted
- date: 2026-10-03

## 背景

一个工作区（源方）想让另一个工作区（看方）的人只读看到自己若干项目的进展，又不想把这些人拉进来当成员。现成的「访客」档位看起来能凑合用：把对方的人一个个邀请成访客，再把项目共享给访客。但访客是**源方的成员**：每个人都要单独邀请，对方换人时还要跟着改。访客一旦成为成员，就能走源方所有既有接口（Issues、Projects、搜索、通知、WebSocket），每个接口都靠自己的过滤把访客挡在外面。只要有一个接口的过滤漏了，泄露的就是整条接口返回的全部字段，描述、评论、附件都在里面。

## 决策

1. **连通是两个工作区之间的关系，不是成员关系。** 表 `workspace_link` 记录「源方 → 看方 + 勾选的项目」。看方的人身份不变，在源方没有任何成员行，源方的既有接口一个都进不去（中间件按成员身份就直接 404）。
2. **只有一个出口。** 看方读取源方数据只能经 `internal/workspacelink` 出去：`GET /api/workspace-links/{id}/view`，以及聊天挂只读参考项目用的 `GET /api/workspace-links/projects` 和每次 run 认领时的重读。它们返回白名单 DTO：项目的标题、图标、状态、完成数和**项目上下文**（描述、资源的仓库地址和本地目录路径、项目记忆那一行），任务的编号、标题、状态、优先级、负责人名字、截止日和更新时间。任务描述、评论、附件、自定义属性、任务 ID、资源的机器信息（daemon、执行模式）都不在里面。DTO 字段有快照测试钉住，加字段就得改测试。
3. **判定集中在 `internal/workspacelink`。** `Decide(op, side, actor)` 一张表决定谁能做什么，测试把每一格都写死了。读取时再按源方的规则过滤：只看勾选的项目，项目和任务都必须不是 private；按「工作区可见」读取，不借任何人的身份。
4. **所有拒绝都是同一个 404 “link not found”。** 不存在、未接受、已断开、不是你这边、你是访客、项目被取消勾选，回的都是同一句话，不告诉对方哪一种。
5. **从看方这边拉（DENE-1582）。** 一个人同时是源方所有者、又是看方所有者或管理员时，可以在看方的设置里直接选源方的项目：一条连通要的两个决定（源方所有者发起、看方接受）他都有权做，`Pull` 在同一个事务里各记一条审计，连通立即生效。不满足就拒绝并说明要请源方所有者发起，不新增「申请」状态。
6. **共享项目就是共享项目上下文（DENE-1643）。** 不另设开关：源方勾选一个项目，看方就能读它的描述、资源和项目记忆，建连通的页面要把这句话写给源方看。看方的聊天可以把它挂成「只读参考项目」，它只进简报里的参考段，永远不是 run 的工作项目：不决定代码来源，不在源方本地目录开 worktree 或提交，仓库只能 checkout 来读、不能推。本机没有那个目录时，简报用一句话说明，不报错。每次 run 认领都按发起人的身份重读一次连通，断开或取消勾选后下一次 run 就不再注入，聊天里显示为失效。
7. **智能体不管连通本身。** 带任务令牌的调用只能 `list` 和 `view` 自己所在工作区的连通，发起、改项目、接受、断开、开关托管一律 403。
8. **可托管是第二个出口，只开给看方的智能体（DENE-1663）。** 源方所有者可以把一条连通设为「可托管」（同时拥有两边的人也可以从看方开关，两边各记一条审计）。打开后，看方智能体的 run 在请求上带 `X-Linked-Workspace: <源方>`，就能以**这次 run 的发起人**的身份操作源方的任务和自动化，执行仍在源方。这是对「任务令牌只能用在绑定工作区」（MUL-2600）唯一的例外，由 `internal/workspacelink` 的 `Managed` 中间件在认证之后、所有工作区门之前判定，每次调用都重查：
   - 源方 → 看方的连通是 active 且托管开着；
   - 令牌对应的 run 还在跑，发起人是源方成员，`Decide(OpManageRemote)` 允许他的档位（成员及以上，访客不行）；
   - 路由在白名单里：任务的列表、读取、新建、改（状态、负责人、优先级、标签、属性、描述）、评论；自动化的列表、读取、新建、改（内容、触发时间）、暂停/恢复、立即运行、删除；以及解析名字要用的只读查询（标签、属性、状态、项目、小队、智能体、成员列表）。成员管理、工作区设置、MCP、智能体配置、连通管理和其余接口都不开。
   通过后请求改写成发起人在源方的普通请求，后面的访客门和各接口自己的权限照常按他在源方的档位判。范围是整个源方工作区，不限于勾选的项目。关掉托管或断开连通，下一次调用就被拒。拒绝统一是 403，不说明是哪一条没过。
   每次写入成功后留痕：`workspace_link_audit` 记一条 `managed_write`（发起人、看方工作区、智能体、路由）；任务上另记一条 `linked_write` 动态，显示为「<发起人> 经 <看方>·<智能体> 代办」；自动化上另记一条 `autopilot_linked_change`（新建时取响应里的 id），用 `GET /api/autopilots/{id}/linked-changes` 或 `multica autopilot linked-changes` 查。

## 理由

- 访客方案的漏洞面是「源方所有接口 × 每个字段」，单一出口的漏洞面只有一个接口和一份白名单。
- 连通不改四档档位矩阵的任何一格，权限底座不需要为它加例外。
- 断开后下一次读取就失效，不依赖缓存失效或会话过期。

## 后果

- 看方能看到的东西只有白名单这么多。项目上下文（DENE-1643）是加进白名单的第一批字段：源方写在项目描述和记忆里的内容会被看方的智能体读到。要再加字段（例如任务详情、评论），得改 DTO、快照测试和这份 ADR，不能顺手把既有接口开给看方。
- 一条连通只有一个看方；要给多个工作区看就建多条连通。实时推送不在范围内；看方写入只有可托管这一条路，而且只给智能体、只在白名单路由上。
- 可托管让看方智能体按发起人在源方的权限干活，等于把这个人在源方的写权限借给了看方的 run。所以开关只给源方所有者，范围宁窄勿宽：白名单之外的接口要开，得改 `managed.go` 的路由表、它的测试和这份 ADR。
- 审计记录写在 `workspace_link_audit`，双方所有者都能看。
