# ADR-0007: 上下文注入原则：简报只写动词，体积有闸门

- status: accepted
- date: 2026-10-05

## 背景

智能体开工只需要知道四件事：我是谁、这回要干嘛、活干到哪了、手里有哪些工具。第四件被写成了说明书，官方和后来的魔改又都是一段段往简报里加。2026-10-04 在 kun 上实测，不含项目描述、用户画像、技能清单时，issue 票开工前平台固定写入约 26KB（工作流和关单决策表 10KB、命令清单 7KB、后台安全 2.3KB、标题规则 1.6KB），聊天约 14KB。简报每个任务都要读、每次续跑都要付，加一段容易，没人负责删。

## 决策

1. **规则住在服务端，简报只写动词。** 服务端能校验的规则，做进命令，让命令自己拒绝并说清缺什么；简报不复述决策表。报错就是说明书。
2. **读状态，不读历史。** 目标、已拍板的事、做到哪、在等什么这类状态由平台维护，开工读状态，翻旧账按需查。
3. **不变的放前面，变的放后面。** 简报对同一个智能体基本不变，能吃缓存；每回合变的内容走回合消息，不进简报。
4. **说明书按需加载，体积有闸门。** 命令细节放 `--help` 和 `multica-platform` skill，用到才读。`server/internal/daemon/execenv` 的体积测试按 issue / chat / quick-create / autopilot 四种任务类型限定简报字节数，涨过上限就红。

### 往简报加内容前的三问

新魔改想往简报里加一段话，依次回答：

| 问 | 答「是」就不进简报 |
| --- | --- |
| 服务端能校验吗？ | 做进命令，让命令拒绝并说明缺什么，简报最多留一句动词 |
| 只在某个动作时才用到吗？ | 放该命令的 `--help`，或 `multica-platform` skill 的对应 reference |
| 每回合都会变吗？ | 放回合消息（`daemon.BuildPrompt`），不进简报；放进去会让缓存前缀每次失效 |

三问都答「否」，才可以进简报：它必须是每个任务开工前都要知道、服务端又拦不住、也不随回合变化的事（身份、代表谁、项目与代码位置这一类）。进简报时在 PR 里写明三问的答案。

### 体积闸门怎么用

- 测试 `TestBriefSizeBudget` 用不含项目和用户内容的最小上下文渲染四种简报，断言字节上限；上限先设在现状略上方，只防继续变厚。
- 测试失败时不要抬高上限，按三问把新文字搬出简报。
- 瘦身改动合入后，同一个 PR 里把上限收紧到新的实测值上方（`TestBriefSizeBudgetIsTight` 会在上限比实测宽 1.2KB 以上时报红）。目标值是 issue ≤ 8KB、chat ≤ 6KB，到位后去掉余量。

## 理由

- 简报是每个任务的固定成本，只增不减时成本没有天花板；闸门把“要不要加”变成一次必须有人回答的问题。
- 服务端校验比简报里的文字可靠：文字要智能体记住并照做，校验不依赖这一点。
- 缓存前缀稳定（MUL-5377）和体积小是同一个方向：简报里只有不变的东西，才既短又吃缓存。

## 后果

- 上下文注入做减法这一组改动（状态卡、简报瘦身、续跑只带状态卡）按这份原则取舍，每一步合入后收紧体积上限。
- DENE-1329 落地后实测：issue 约 5.5KB、chat 约 3.5KB、quick-create 约 4.8KB、autopilot 约 3.2KB，都低于目标；上限仍贴着实测值，目标与实测之间的差额不是可以长回去的空间。评论写法搬进 `multica issue comment add --help`，标题和正文格式搬进 `multica issue create --help`，验收席的通过/打回写进 `multica issue close --help`。
- 新增魔改命令要自己写清报错和 `--help`，不能指望在简报里补一段。
- 体积闸门只量平台固定文字，不量项目描述、用户画像、技能清单这些随任务而来的必要上下文。
