[프로젝트](/projects) 리소스는 이 작업 묶음에 어떤 코드가 필요하며 어디에서 실행할지 에이전트에게 알려 줍니다. 리소스는 프로젝트에 계속 연결되어 있으므로 각 태스크에 저장소 주소나 로컬 경로를 반복해서 붙여 넣을 필요가 없습니다.

현재 두 가지 리소스를 지원합니다.

| 리소스 | 적합한 경우 | 실행 위치 |
|---|---|---|
| **GitHub 저장소** | 팀이 공유하는 코드베이스이며 런타임이 checkout을 관리해야 할 때 | 런타임이 관리하는 작업 디렉터리 |
| **로컬 디렉터리** | 이미 존재하는 checkout, 매우 큰 저장소, 로컬 변경 내용을 직접 확인해야 할 때 | 지정한 컴퓨터의 원본 디렉터리 |

## 어떤 구성이 자신에게 맞는지

여섯 가지 조합이면 거의 모든 경우를 다룹니다. 첫 번째 열에서 자신의 상황을 찾고, 아래 각 절에서 그 구성 요소를 설명합니다.

| | 어떤 상황인지 | 무엇을 연결하는지 | 작업이 일어나는 위치 | 누구의 디스크이며 누가 정리하는지 | 동시 실행 | 변경 사항이 돌아오는 방식 |
| --- | --- | --- | --- | --- | --- | --- |
| **A** | 로컬 git 저장소, 원격이 있든 없든 — **기본값** | 로컬 디렉터리 · **직접** | **자신의 디렉터리** | 추가 공간을 쓰지 않음 | 그 디렉터리에서 한 번에 하나의 실행, 이후 실행은 대기 | 작업 사본이 제자리에서 수정됩니다 — 직접 `git diff`하고 되돌립니다 |
| **B** | 로컬 git 저장소이고, 정말로 여러 실행을 동시에 돌려야 함 | 로컬 디렉터리 · **병렬** | **저장소 옆의 작업 사본 디렉터리** — 기본값은 `<repo>.multica-worktrees/<run>` | **자신의 디스크.** 기본적으로 아무것도 정리하지 않으며, 자동 정리를 켜면 병합되었고 N일보다 오래되었고 커밋되지 않은 변경이 없는 사본만 정리 | 같은 디렉터리의 실행들이 동시에 진행 | 브랜치가 이미 자신의 저장소에 있고, 작업 사본은 직접 열어볼 수 있는 곳에 남습니다 |
| **C** | Git이 전혀 없는 일반 로컬 폴더 | 로컬 디렉터리 · **직접** | **자신의 디렉터리** | 추가 공간을 쓰지 않음 | 한 번에 하나, 이후 실행은 대기 | 제자리에서 수정 — diff도 없고 **되돌릴 수도 없습니다** |
| **D** | 저장소 여러 개나 서로 별개의 작업 묶음 여러 개를 담은 디렉터리 하나 | 로컬 디렉터리 · **공유** | **자신의 디렉터리**, 잠금 없음 | 추가 공간을 쓰지 않음 | 동시 실행이지만 아무것도 잠기지 않으므로 두 실행이 서로를 방해할 수 있습니다 | 제자리에서 수정 |
| **E** | 클라우드 프로젝트이거나, 이 컴퓨터에 코드 사본이 없음 | GitHub 저장소 | Multica 워크스페이스의 checkout | Multica의 디스크이며 일반 정리 주기로 회수 | 본질적으로 동시 실행 | 원격으로 push된 브랜치 |
| **F** | 아무것도 연결하지 않음 — 질문과 대화만 | 아무것도 연결하지 않음 | **하나의 공용 세션 폴더**(실행마다 폴더 하나가 아니라 대화마다 하나) | Multica의 디스크이며 크게 늘지 않음 | — | 산출물은 공용 폴더 아래 이 대화의 폴더에 남습니다 |

## 리소스가 실행에 들어가는 방식

에이전트가 프로젝트 안의 태스크를 처리하면 Multica가 프로젝트 이름, 프로젝트 설명, 리소스 목록을 실행 컨텍스트에 추가하고, 리소스 목록을 `.multica/project/resources.json`에 기록합니다 — 실행이 어디에서 일어나는지에 따라 작업 디렉터리에 기록되기도 하고 데몬 자체의 실행별 폴더에 기록되기도 합니다. 아래 "실행 중 기록되는 내용"을 참고하세요.

워크스페이스에 연결된 저장소 목록은 항상 실행 컨텍스트에 포함됩니다. 프로젝트에 연결된 저장소는 그중 이 작업 묶음에서 사용할 코드와 기본 ref를 지정합니다.

로컬 디렉터리는 연결된 데몬에만 적용되며, 저장소보다 우선합니다. 실행을 가져가는 컴퓨터에 해당 프로젝트의 로컬 디렉터리가 있으면 프로젝트가 GitHub 저장소도 지정했는지와 무관하게 그 디렉터리에서 실행됩니다. 저장소는 그 머신의 어떤 로컬 디렉터리에도 프로젝트 코드가 없을 때만 사용되며, 디렉터리가 없거나 사용할 수 없으면 새 clone으로 조용히 대체되지 않고 그대로 보고됩니다. 다른 컴퓨터는 계속 프로젝트의 GitHub 저장소나 워크스페이스 저장소를 사용합니다.

## GitHub 저장소 추가

프로젝트를 열고 **리소스**에서 "리소스 추가"를 선택합니다. 워크스페이스에 이미 연결된 저장소를 고르거나 Git URL을 붙여 넣을 수 있습니다. 워크스페이스 저장소는 **설정 → 코드 저장소**에서 관리합니다. GitHub를 연결한 뒤 같은 페이지에서 **GitHub에서 선택**을 통해 App에 승인된 저장소를 가져올 수 있습니다.

저장소는 GitHub로 제한되지 않습니다. 런타임이 접근할 수 있는 Git URL이라면 모두 저장소 리소스로 사용할 수 있습니다. 자체 배포한 Multica에서는 **설정 → 연동 → Git 코드 호스팅**에서 자체 호스팅 Forgejo, Gitea, GitLab을 연결할 수도 있습니다. [자체 호스팅 Git 코드 호스팅](/vcs-integration)을 참고하세요.

프로젝트를 만들 때 **Repos**에서 바로 저장소를 선택할 수도 있습니다. 하나의 프로젝트에 여러 GitHub 저장소를 연결할 수 있습니다.

리소스의 `ref`에는 이후 checkout에서 기본으로 사용할 브랜치, tag, commit을 지정할 수 있습니다. `default_branch_hint`는 에이전트에게 기본 브랜치 힌트만 제공하며 강제로 브랜치를 전환하지 않습니다.

## 로컬 디렉터리 추가

브라우저는 컴퓨터의 폴더를 선택할 수 없으므로 로컬 디렉터리 추가 화면은 Desktop에서만 제공됩니다.

<Callout type="info">
**로컬 디렉터리는 프로젝트에 코드를 주는 기본 방식이며, 비상구가 아닙니다.** 실행을 가져가는 컴퓨터에 해당 프로젝트의 로컬 디렉터리가 있으면 실행은 그것을 사용하며, 저장소는 그 코드의 사본이 없는 머신을 위한 대체 수단입니다.

폴더가 반드시 git 저장소여야 하는 것은 아닙니다. 그렇지 않을 때 무엇을 포기하는지는 아래 "로컬 Git을 만들지, 만들지 않을지"를 참고하세요.
</Callout>


1. Desktop의 로컬 데몬이 온라인인지 확인합니다.
2. 프로젝트의 **리소스**를 엽니다. 프로젝트 생성 대화상자의 **로컬 디렉터리** 탭에서도 프로젝트가 만들어지기 전에 같은 선택을 할 수 있습니다.
3. "로컬 디렉터리 추가"를 선택한 뒤 사용할 폴더를 고릅니다.
4. 실행이 그 폴더를 어떻게 사용할지 고릅니다 — **직접**, **병렬** 또는 **공유**이며, 차이는 "실행이 디렉터리를 공유하는 방식"에 설명되어 있습니다. 새로 연결하는 디렉터리는 항상 **직접**으로 시작합니다. 방금 고른 폴더 안에서 실행되며 디스크를 추가로 쓰지 않습니다. **병렬**은 명시적으로 선택해야 합니다 — 실행마다 완전한 작업 사본을 사용자 본인의 드라이브에 만들기 때문입니다. 그 사본이 어느 폴더에 놓이는지는 고르기 전에 대화 상자가 알려줍니다. **공유**는 여러 저장소나 서로 별개의 작업 묶음 여러 개를 담은 디렉터리를 위한 모드입니다. 그 자리에서 바꿀 수 있고, 나중에 **리소스**에서 디렉터리 옆 연필 아이콘으로도 바꿀 수 있습니다.

이전에 연결한 디렉터리는 저장할 때의 모드를 그대로 유지합니다 — 기존 설정이 모르는 사이에 바뀌지 않습니다.

디렉터리는 절대 경로여야 하고 이미 존재해야 하며 현재 데몬이 읽고 쓸 수 있어야 합니다. 시스템 루트와 드라이브 루트(`/`, `C:\`), 사용자 홈 디렉터리 자체 및 각 홈 디렉터리의 상위 경로(`/Users`, `/home`, `/root`), 그리고 `/etc`, `/var`, `/tmp`, `/usr`, `/opt` 같은 시스템 디렉터리는 거부됩니다. 선택한 경로가 심볼릭 링크이면 실제 경로를 먼저 해석한 뒤 같은 규칙으로 다시 확인하며 직렬 잠금도 실제 경로를 기준으로 적용됩니다.

한 컴퓨터에서 프로젝트는 로컬 디렉터리를 **여러 개** 연결할 수 있습니다 — 서로 무관한 일반 폴더 4개여도 되고, 저장소 하나와 별도의 문서 체크아웃이어도 됩니다. 두 번 연결할 수 없는 것은 같은 디렉터리(해석된 실제 경로로 판단하므로 심볼릭 링크와 그 대상은 하나로 셉니다)와, 그 컴퓨터에 이미 있는 저장소의 두 번째 체크아웃입니다. 서로 다른 컴퓨터에서는 같은 프로젝트에 각자의 디렉터리를 연결할 수 있습니다.

**한 번의 실행은 한 디렉터리에만 씁니다.** 어느 디렉터리인지는 두 단계 규칙을 따르며, 서버에서 한 번 계산되어 런타임과 UI에 함께 전달됩니다. 태스크가 리소스를 명시적으로 지정하면 그 리소스를 사용하고, 사용할 수 없으면 그 이유를 밝히며 실행이 실패합니다. 그렇지 않으면 실행은 **목록에서 그 컴퓨터의 첫 번째 로컬 디렉터리**를 사용합니다. 따라서 첫 번째 항목이 이 머신의 기본 작업 디렉터리입니다 — 목록을 드래그하거나 그 컴퓨터의 디렉터리에 있는 이동 버튼으로 바꾸세요. 나머지 디렉터리는 읽기 전용으로 에이전트에 전달되고 브리프에도 기록되므로, 읽을 수는 있지만 작업해도 되는 두 번째 장소로 취급되지 않습니다.

### 로컬 Git을 만들지, 만들지 않을지

일반 폴더도 로컬 디렉터리로 쓸 수 있습니다. 연결하면 에이전트가 Git과 전혀 무관하게 제자리에서 수정합니다. 이런 폴더를 추가할 때 Desktop은 그 안에 로컬 Git 저장소를 만들 것을 제안합니다 — 그리고 그 제안은 **GitHub과 아무 관련이 없습니다**: 여기서 만든 저장소는 이 컴퓨터에서 변경 사항을 기록할 뿐 아무것도 업로드하지 않습니다. 건너뛸 수 있으며, 그러면 그 행에 "버전 관리 없음" 배지가 남습니다.

건너뛰었을 때 포기하는 것은 무슨 일이 있었는지에 대한 기록입니다. `git diff`도 없고, 되돌아갈 브랜치도 없고, 에이전트가 덮어쓴 파일을 복원할 방법도 없습니다. 내용이 중요한 폴더라면 로컬 저장소를 만드는 것이 저렴한 보험입니다.

<Callout type="warning">
기본값인 `in_place` 모드에서 로컬 디렉터리는 격리된 환경이 아닙니다. 에이전트가 현재 브랜치와 커밋하지 않은 파일을 직접 보고 수정하며, Multica는 브랜치 전환, stash, commit, push, PR 생성을 자동으로 수행하지 않습니다. 워크트리 모드는 이 점을 바꿉니다 — 아래 “실행이 디렉터리를 공유하는 방식”을 참고하세요.
</Callout>

## 실행이 디렉터리를 공유하는 방식

로컬 디렉터리에는 세 가지 실행 모드가 있으며 `execution_mode`로 리소스별로 설정합니다. Desktop에서는 **직접**, **병렬**, **공유**로 표시하며, API와 CLI, 이 문서의 나머지 부분에서는 식별자를 사용합니다.

일반적인 저장소에서 실제로 중요한 것은 직접과 병렬 두 가지입니다. 세부 설명에 앞서 그 선택의 갈림길을 먼저 정리합니다:

| | 직접(`in_place`) — 기본값 | 병렬(`worktree`) |
| --- | --- | --- |
| 디스크 | 추가 공간을 쓰지 않음 | 실행마다 전체 작업 사본과 그 사본 자체의 의존성까지, 프로젝트 디스크에 사용 |
| 동시 실행 | 디렉터리에서 한 번에 하나의 실행, 이후 실행은 대기 | 같은 디렉터리에서 임의 개수의 실행 |
| 실패했을 때의 현장 | 자신의 디렉터리 — 에이전트가 작업하면서 자신의 작업 사본을 수정하고, 남긴 것은 이미 자신이 있는 그 자리에 그대로 있습니다 | 저장소 옆에 있는, 직접 열어볼 수 있는 작업 사본; 자신의 작업 사본은 결코 건드리지 않습니다 |
| 정리 주체 | 정리할 것이 없음 | 기본적으로 사용자 자신이며, 자동 정리는 선택 사항이고 병합되었고 깨끗한 사본만 삭제 |
| 위험 | 에이전트와 편집기가 같은 트리에 씀 | 실행들이 서로 격리됨 |

**기본값은 직접**이며 가장 저렴합니다. 추가 디스크도 없고 정리할 것도 없습니다. 병렬은 정말로 여러 태스크를 동시에 수행하는 디렉터리를 위한 것으로, 자신의 머신에 있는 디스크와 사용자가 직접 정리해야 하는 작업 사본을 대가로 동시성을 얻습니다.

### `in_place`(기본값) — "직접"

에이전트가 사용자의 디렉터리에서 직접 작업하며, 실행은 한 번에 하나씩 진행됩니다. 두 실행이 같은 실제 디렉터리를 사용하면 나중에 도착한 실행이 `waiting_local_directory` 상태로 들어가 앞선 실행이 디렉터리를 해제할 때까지 기다립니다. 서로 다른 심볼릭 링크 경로가 같은 디렉터리를 가리켜도 직렬로 실행됩니다.

기다리는 동안 디렉터리는 변경되지 않습니다. 대기 중인 실행은 취소할 수 있으며 취소하지 않으면 디렉터리를 사용할 수 있을 때까지 계속 기다립니다.

### `worktree` — "병렬"

각 실행이 저장소의 독립된 [git 워크트리](https://git-scm.com/docs/git-worktree)를 받으며, 워크트리는 **사용자 본인의 드라이브에서 저장소 옆에** 생성됩니다 — 기본값은 `<repo>.multica-worktrees/<run>`입니다. **같은 디렉터리에 대한 실행들이 동시에 진행되고 어느 것도 대기하지 않으며**, 어느 것도 사용자의 작업 사본에 쓰지 않습니다.

사본은 저장소 안이 아니라 옆에 놓이므로 사용자의 `git status`에 나타나지 않고 `.gitignore`에 무언가를 추가할 필요도 없습니다. Multica의 작업 공간이 아니라 사용자의 디스크에 두는 이유는 하나입니다. 실행이 실패했을 때 그 사본이 어디까지 진행했는지를 보여주는 유일한 기록이며, 동의한 적 없는 정리 주기에 따라 사라져서는 안 되기 때문입니다. 대신 그 용량은 사용자의 것입니다 — 아래 "작업 사본 정리하기"를 참고하세요.

이 모드는 커밋이 하나 이상 있는 git 저장소를 요구합니다. 그렇지 않으면 조용히 직렬 실행으로 되돌아가는 대신 명시적인 오류로 실패합니다. 해당 머신의 런타임도 이 모드를 구현하고 있어야 합니다. 런타임은 연결할 때 그 기능을 선언하며, Multica는 버전 번호가 아니라 이 선언을 기준으로 판단합니다 — 개발 빌드는 구현이 전혀 없는 채로 충분히 새것처럼 보이는 버전 문자열을 가질 수 있기 때문입니다. 이 선언은 두 번 확인됩니다. 해당 머신의 런타임이 기능을 선언하지 않는 동안에는 리소스 저장이 거부되고 그 머신의 앱을 업데이트하라는 안내가 표시되며, 각 실행은 실제로 그것을 가져간 런타임을 기준으로 다시 확인됩니다 — 따라서 리소스를 저장한 뒤 다운그레이드된 머신에서는 실행이 조용히 제자리에서 진행되는 대신 이유와 함께 취소됩니다. `worktree`를 요청하는 것은 격리를 요청하는 것이며, 대신 작업 사본을 수정하는 것이 대체 동작이 되는 일은 없습니다.

에이전트가 보는 것과 사용자가 받는 것:

- **에이전트는 `HEAD`가 아니라 지금 보고 있는 상태에서 시작합니다.** 커밋하지 않은 수정과 추적되지 않은 파일이 워크트리로 재현되므로, 더 이상 갖고 있지 않은 코드를 검토하지 않습니다. 사용자의 작업 사본, 인덱스, stash 목록은 절대 건드리지 않습니다. 그 상태를 충실히 재현할 수 없으면 — 재현 한도(2000개 파일 / 200 MiB)를 넘는 추적되지 않은 콘텐츠가 있는 경우 포함 — 알아볼 수 없는 트리에서 시작하는 대신 실행이 실패합니다. 보통은 아직 무시되지 않은 빌드 산출물을 gitignore에 추가하거나 정리하면 해결됩니다.
- **결과물은 저장소 안의 브랜치**이며 실행마다가 아니라 태스크마다 하나씩, `agent/<agent>/<issue>` 형식입니다(채팅은 `agent/<agent>/chat-<session>`). 실행의 **실행 세부 정보** 패널에 브랜치 이름이 표시되고 복사할 수 있으며, `git branch`로도 찾을 수 있습니다. `git log` / `git diff`로 검토한 뒤 병합할지 cherry-pick할지 직접 결정합니다. Multica가 대신 병합하지 않습니다. 도중에 실패한 실행도 브랜치를 보고합니다. 에이전트가 만든 부분은 이미 커밋되어 있기 때문입니다.
- **후속 실행은 지난 실행이 멈춘 지점에서 이어집니다.** 같은 태스크에 다음 댓글이 달리면 그 브랜치를 다시 체크아웃하므로, 에이전트는 방금 전달한 작업 위에서 이어서 일합니다. `HEAD`에서 새로 시작해 지난 변경이 다른 브랜치에 남겨지는 일은 없습니다. 다시 적용되는 것은 지난 실행 이후 사용자가 자기 디렉터리에서 바꾼 부분뿐이며, 나머지는 브랜치가 이미 갖고 있습니다. 브랜치를 병합하면 다음 실행은 다시 사용자의 `HEAD`에서 시작합니다. 한 태스크에서 두 실행이 겹치면 나중 실행이 앞선 실행의 작업에서 `agent/<agent>/<issue>-<task>`로 갈라져 나갑니다. git은 브랜치 하나당 worktree 하나만 허용하기 때문입니다.
- **사용자의 변경이 에이전트의 작업과 충돌하면 에이전트가 해결합니다.** 에이전트가 고친 것과 같은 줄을 사용자가 다시 고치면 git은 어느 쪽이 맞는지 판단할 수 없습니다. 그 실행은 충돌이 남은 워크트리에서 시작하며, 다른 무엇보다 먼저 병합을 끝내라는 지시를 받습니다(그 워크트리에서 `git status`가 병합되지 않은 파일을 보여줍니다). 병합되지 않은 파일이 하나라도 남은 실행은 아무것도 전달하지 않습니다. 실행은 실패하고 워크트리는 보존되며, 다음 실행이 같은 변경을 다시 제안하므로 사용자의 변경이 조용히 사라지지 않습니다.
- **Multica 소유임이 확인된 브랜치만 이어받습니다.** 이어받을지는 이름이 아니라 소유 기록으로 결정됩니다. 기록에는 어느 대화의 것인지와 함께 그 브랜치가 마지막으로 놓였던 커밋도 적혀 있습니다. 사용자가 직접 만든, 우연히 `agent/<agent>/<issue>`라는 이름의 브랜치는 체크아웃되지도, 커밋이 추가되지도, 이전 실행의 결과로 읽히지도 않습니다. 기록된 커밋을 더는 포함하지 않는 브랜치도 마찬가지여서, Multica의 브랜치를 지우고 같은 이름으로 새로 만들거나 다른 히스토리로 force-move해도 안전합니다. 그런 경우 실행은 `agent/<agent>/<issue>-<id>`를 사용합니다. 전달된 브랜치 위에 커밋하는 것은 정상적인 사용이며, 이어받기는 그대로 유지되고 사용자의 커밋은 다음 실행에 그대로 포함됩니다. 모든 브랜치는 자기 자신의 베이스라인 커밋으로 시작합니다. 첫 실행이 시작한 시점의 트리를 표시하며, 나중에 브랜치를 식별하는 것이 바로 이 커밋이고 `git diff <baseline>..<branch>`가 정확히 에이전트의 작업이 됩니다. 브랜치를 기록하지 못한 실행은 — 도중에 실패했거나, 기록을 쓰지 못했거나, 사용자의 변경을 브랜치에 반영한 커밋 이전으로 워크트리를 되돌린 경우 — 실패로 보고되고 워크트리를 남기며, 이후 실행은 자기 것임을 증명할 수 없는 브랜치를 이어받는 대신 새 브랜치에서 시작합니다.
- **조용히 사라지는 것은 없습니다.** 에이전트가 커밋하지 않고 남긴 변경 사항은 워크트리가 제거되기 전에 해당 브랜치로 커밋되며, **실행이 도중에 실패한 경우에도 마찬가지입니다.** 드물게 그 커밋 자체를 할 수 없는 경우 — 예를 들어 `commit.gpgSign`이 켜져 있고 런타임이 서명 키를 사용할 수 없는 저장소 — 워크트리는 제거되지 않고 의도적으로 유지되며, 실행은 실패로 보고되고, 저장소에서 `git worktree list`를 실행하면 해당 변경 사항이 있는 디렉터리를 확인할 수 있습니다.
- **아무것도 변경하지 않은 실행은 아무것도 남기지 않습니다.** 해당 브랜치는 `git branch`에 빈 항목으로 남지 않고 삭제됩니다. 다만 이전 실행의 작업을 담고 있는 태스크 브랜치는 항상 유지됩니다.

저장소에는 두 가지가 남습니다. 브랜치, 그리고 브랜치마다 하나씩 있는 숨은 ref(`refs/multica/local-state/` 아래)입니다. 후자는 그 브랜치의 소유자와 마지막으로 이어받을 때 사용자 디렉터리의 내용을 기록합니다. 숨은 ref는 `git branch`에 나타나지 않으며 `git for-each-ref refs/multica`로 확인할 수 있습니다. Multica는 브랜치를 지울 때 함께 지우고, 사용자가 직접 지운 브랜치의 ref는 그 저장소에서 다음 실행이 시작될 때 정리합니다. `git for-each-ref --format='%(refname)' refs/multica | xargs -n1 git update-ref -d`로 한 번에 지울 수도 있습니다.

### `shared` — "공유"

실행이 사용자의 디렉터리에서 **잠금 없이** 동시에 진행됩니다. 공유 모드는 여러 저장소나 서로 별개의 작업 묶음 여러 개를 담은 디렉터리를 위한 것으로, 각 태스크가 Multica의 직렬화에 의존하는 대신 저장소별 워크트리로 스스로를 격리합니다. 복사되지도, 대기하지도 않으며 잠그지도 않으므로, 정말로 같은 트리를 건드리는 두 실행은 서로를 방해할 수 있습니다. 그 디렉터리 안의 작업이 실제로 서로 독립적일 때만 선택하세요. 병렬과 달리 git 저장소도, 결과를 브랜치로 돌려주는 것도 필요하지 않습니다 — 그 부분은 사용자 자신의 규칙입니다.

### 작업 사본 정리하기

정상적으로 끝난 실행은 자신의 작업 사본을 제거합니다. 남는 것은 실행을 **끝내지 못한** 경우 — 해결되지 않은 병합, 실패한 커밋, 멈춘 머신 — 이며, 이는 의도적으로 디스크에 남습니다. 그 실행의 상태를 확인할 수 있는 유일한 곳이기 때문입니다.

남은 사본의 자동 정리는 프로젝트가 아니라 **컴퓨터의 설정**입니다. 디스크는 컴퓨터의 속성이기 때문입니다. 설정은 Desktop의 데몬 설정에 있으며 **기본값은 꺼짐**입니다. 사본 목록과 각 사본이 어떻게 처리될지는 스위치가 켜져 있든 꺼져 있든 표시됩니다. 켜기 전에 정책의 판정을 읽어볼 수 있도록 하기 위해서입니다.

스위치를 켜더라도 사본이 삭제되는 것은 다음을 **모두** 만족할 때뿐입니다:

1. Multica가 만든 것일 것 — 사용자가 `git worktree add`로 만든 워크트리는 절대 건드리지 않습니다;
2. 어떤 실행도 사용 중이 아닐 것;
3. 마지막 실행이 설정한 기간(기본 14일)보다 오래되었을 것;
4. 그 안의 `git status --porcelain`이 비어 있을 것 — `.gitignore`가 덮는 파일(`node_modules` 등)은 세지 않습니다;
5. 그 작업이 이미 트렁크 브랜치에 들어가 있을 것 —— 브랜치가 트렁크에 포함되어 있거나, 변경이 squash되어 들어가 있으면 됩니다. squash 머지는 작업을 새 커밋으로 다시 쓰므로 브랜치 자체가 트렁크의 조상이 되는 일은 없습니다. 조상이 아니라 내용으로 비교해야 squash 방식의 저장소에서도 이 조건에 도달할 수 있습니다. "원격 브랜치가 사라졌다"와 "풀 리퀘스트가 병합됐다"는 의도적으로 채택하지 않았습니다. 앞은 병합 후 삭제된 브랜치와 한 번도 push하지 않은 브랜치를 구분할 수 없고, 뒤는 내 디스크를 정리하는 일을 네트워크와 GitHub에 의존하게 만들기 때문입니다.

하나라도 어긋나면 사본은 보관되고, 설정 화면이 어떤 조건인지 알려줍니다. 가장 중요한 것은 4번입니다. 브랜치가 병합되었다는 사실은 디렉터리 안에 커밋되지 않은 무언가가 남아 있는지에 대해 아무것도 말해주지 않으며, 그것이 바로 실패한 실행이 남기는 것입니다. 삭제는 항상 `git worktree remove`를 거치므로, 저장소에 오래된 `.git/worktrees` 항목이 남아 같은 이름을 나중에 쓰지 못하게 되는 일은 없습니다.

그 목록에서 사본 하나만 정리할 수도 있습니다. 이는 "어느 사본인지"를 지정하는 것이지 "규칙을 무시"하는 것이 아닙니다 — 같은 다섯 조건이 그 시점의 디렉터리를 기준으로 다시 확인됩니다.

**셀프 호스팅 운영자 주의:** 이 모드의 격리는 서버가 강제합니다(리소스 저장 시 한 번, 런타임이 각 실행을 가져갈 때 다시 한 번). 따라서 런타임을 언제 다운그레이드하더라도 차단됩니다. 유일하게 차단되지 않는 조합은 이 모드를 구현하지 않은 런타임이 연결된 상태에서 서버를 이 기능 이전 빌드로 롤백하는 것입니다 — 구버전 서버에는 이 게이트가 없고, 그런 런타임은 `execution_mode`를 무시한 채 실행을 원본 디렉터리에서 그대로 처리합니다. `worktree` 리소스가 존재하는 동안에는 해당 머신의 런타임이 모두 최신이 아닌 한 서버를 이 릴리스 이전으로 롤백하지 마십시오.
</Callout>

<Callout type="info">
워크트리 모드는 git 저장소를 대상으로 합니다. git으로 관리되지 않는 일반 디렉터리는 계속 직렬로 실행됩니다 — 그것이 `in_place`의 역할입니다.
</Callout>

## 아무것도 연결하지 않았을 때: 공용 세션 폴더

해당 머신에 로컬 디렉터리도 저장소도 없는 실행에는 작업할 코드가 없고 파일을 둘 곳만 있습니다. 그렇다고 매번 새 태스크 디렉터리를 받지는 않습니다. 한 대화의 매 턴이 하나의 폴더를 사용하므로(실행마다 폴더 하나가 아니라 대화마다 하나), 한 스레드에서 스무 번 질문해도 스무 개의 폴더가 어디에도 쌓이지 않습니다.

폴더는 에이전트를 실행하는 컴퓨터의 데몬 워크스페이스 루트 아래 `.sessions/<workspace-id>/sessions/<conversation-id>`에 있습니다. 워크스페이스 루트의 기본값은 `~/multica_workspaces`(이름 있는 profile은 `~/multica_workspaces_<profile>`)이며 `MULTICA_WORKSPACES_ROOT`로 옮길 수 있습니다.

이 폴더는 Multica의 것이므로 자동으로 정리됩니다: **기본값이 켜짐**이며, 자신의 드라이브에 있는 병렬 작업 사본과는 반대입니다. 대화의 폴더는 Multica가 만든 것이고, 어떤 실행도 사용 중이 아니고, 보존 기간(기본 14일)을 넘겨 유휴 상태일 때만 삭제됩니다. Desktop의 데몬 설정에서 이 폴더와 그 크기, 그리고 각 대화가 왜 보관되거나 정리되는지를 볼 수 있으며, 그 자리에서 특정 대화를 정리할 수도 있습니다. 스캔은 그 루트를 벗어나지 않습니다. 사용자의 디렉터리와 저장소 옆의 작업 사본은 절대 대상이 되지 않습니다.

## 서버가 실행을 배치할 수 없을 때

실행이 어느 디렉터리에 쓰는지는 런타임이 실행을 가져가기 전에 서버에서 한 번 결정하며, 런타임은 다시 고르지 않고 그 결정을 검증만 합니다. 답을 계산할 수 없으면 다른 디렉터리나 새 원격 checkout으로 대체하지 않고 실행이 실패 코드와 함께 실패합니다: `daemon_cannot_run_mode`, `unknown_execution_mode`, `malformed_resource`, `pinned_resource_not_found`, `pinned_resource_other_machine`, `pinned_resource_unusable`. 각 코드와 그에 대한 다음 단계는 [문제 해결](/troubleshooting#코드-소스-실패-코드)에 정리되어 있습니다.

구버전 런타임은 영향을 받지 않습니다. 서버는 리소스 목록을 실행을 가져가는 런타임이 처리할 수 있다고 선언한 범위로 좁히므로, 여러 로컬 디렉터리나 새 작업 사본 위치 이전의 런타임도 예전과 정확히 같은 리소스를 받습니다 — **업그레이드가 필요하지 않으며** 그 실행은 늘 그랬듯이 동작합니다.

## 실행 중 기록되는 내용

에이전트가 만든 코드 변경 외에도 런타임이 현재 AI 코딩 도구에 필요한 지시 파일과 `.multica/project/resources.json`을 작업 디렉터리에 기록할 수 있습니다. Multica는 실행이 끝나면 자신이 만든 파일을 다시 회수하므로, 직접 모드의 실행은 에이전트의 변경을 빼면 폴더를 원래대로 돌려주고, 병렬 실행은 폴더에 전혀 쓰지 않으며, 공유 실행은 Multica의 파일을 폴더 안에 남기지 않습니다.

Multica가 실행 환경을 정리할 때 연결된 로컬 디렉터리는 삭제하지 않습니다. 에이전트가 이 디렉터리에 만든 변경은 터미널에서 AI 코딩 도구를 직접 실행해 만든 변경과 성격이 같으므로 동일하게 검토해야 합니다.

## CLI로 리소스 관리

```bash
# 프로젝트를 만들면서 저장소 연결
multica project create \
  --title "Agent UX" \
  --repo https://github.com/multica-ai/multica

# 리소스 확인 및 추가
multica project resource list <project-id>
multica project resource add <project-id> \
  --type github_repo \
  --url https://github.com/multica-ai/multica \
  --ref main

# 지정한 데몬의 로컬 디렉터리 연결
multica project resource add <project-id> \
  --type local_directory \
  --local-path /absolute/path/to/repo \
  --daemon-id <daemon-id>

# 로컬 git 저장소를 연결하고 실행을 각자의 워크트리에서 동시에 처리
multica project resource add <project-id> \
  --type local_directory \
  --local-path /absolute/path/to/repo \
  --daemon-id <daemon-id> \
  --execution-mode worktree

# 기존 로컬 디렉터리의 모드 전환
multica project resource update <project-id> <resource-id> --execution-mode worktree
multica project resource update <project-id> <resource-id> --execution-mode in_place


# 리소스 제거
multica project resource remove <project-id> <resource-id>
```

리소스 변경은 이후 생성되는 실행에 적용되며 이미 끝난 실행 기록은 바꾸지 않습니다.
