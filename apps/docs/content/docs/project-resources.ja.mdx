[プロジェクト](/projects)のリソースは、この一連の作業がどのコードを使い、どこで実行するかをエージェントに伝えます。リソースはプロジェクトに紐づいたまま保たれるため、リポジトリの URL やローカルパスをタスクごとに貼り直す必要はありません。

現在サポートされているリソースは 2 種類です。

| リソース | 適した場面 | 実行場所 |
|---|---|---|
| **GitHub リポジトリ** | チームで共有するコードベースで、checkout をランタイムに管理させたい場合 | ランタイムが管理する作業ディレクトリ |
| **ローカルディレクトリ** | 既存の checkout、非常に大きなリポジトリ、またはローカルの変更を直接確認したい場合 | 特定のコンピュータ上の元のディレクトリ |

## どの形が自分に当てはまるか

ほぼすべてのケースは 6 つの組み合わせに収まります。第 1 列で自分の状況を探し、それぞれの部品は以降の各節で説明します。

| | どの状況か | 何を紐づけるか | 作業が行われる場所 | 誰のディスクで、誰が片付けるか | 並行性 | 変更がどう戻ってくるか |
| --- | --- | --- | --- | --- | --- | --- |
| **A** | ローカル git リポジトリ。リモートの有無は問わない — **既定** | ローカルディレクトリ · **直接** | **あなた自身のディレクトリ** | 追加のディスクを消費しません | そのディレクトリでは一度に 1 実行。後から来た実行はキューに入ります | 作業コピーがその場で編集されます — あなたが `git diff` で確認し、自分で元に戻します |
| **B** | ローカル git リポジトリで、本当に複数の実行を同時に走らせる必要がある | ローカルディレクトリ · **並行** | **リポジトリの隣の作業コピーディレクトリ** — 既定では `<repo>.multica-worktrees/<run>` | **あなた自身のディスク。** 既定では誰も片付けません。自動クリーンアップを有効にした場合は、マージ済みで、N 日より古く、未コミットの変更がないコピーだけを削除します | 同じディレクトリ上の実行は並行して進みます | ブランチはすでにあなたのリポジトリにあり、作業コピーはあなたが開ける場所に残ります |
| **C** | Git がまったくない普通のローカルフォルダ | ローカルディレクトリ · **直接** | **あなた自身のディレクトリ** | 追加のディスクを消費しません | 一度に 1 実行。後から来た実行はキューに入ります | その場で編集されます — diff はなく、**元に戻せません** |
| **D** | 1 つのディレクトリに複数のリポジトリ、または複数の独立した作業が入っている | ローカルディレクトリ · **共有** | **あなた自身のディレクトリ**、ロックなし | 追加のディスクを消費しません | 並行ですが何もロックされないため、2 つの実行が互いに踏み合うことがあります | その場で編集されます |
| **E** | クラウドのプロジェクト、またはこのコンピュータにコードのコピーがない | GitHub リポジトリ | Multica ワークスペース内の checkout | Multica のディスク。通常のクリーンアップ周期で回収されます | 本質的に並行です | リモートに push されたブランチ |
| **F** | 何も紐づけていない — 質問と会話のみ | 何も紐づけない | **1 つの共有セッションフォルダ**（実行ごとではなく会話ごとに 1 つ） | Multica のディスクで、しかも小さいままです | — | 成果物は共有フォルダ配下の、この会話のフォルダに残ります |

## リソースが実行に入る仕組み

エージェントがプロジェクト内のタスクを処理するとき、Multica はプロジェクト名、プロジェクトの説明、リソース一覧を実行コンテキストに追加し、リソース一覧を `.multica/project/resources.json` に書き込みます — 実行がどこで行われるかに応じて、作業ディレクトリか、デーモン自身の実行ごとのフォルダのいずれかになります。詳しくは下の「実行中に書き込まれるもの」を参照してください。

ワークスペースに紐づくリポジトリ一覧は、常に実行コンテキストに含まれます。プロジェクトに紐づくリポジトリは、それに加えて、この一連の作業で使うコードとデフォルトの ref を指定します。

ローカルディレクトリは、それを紐づけたデーモンに対してのみ有効で、リポジトリより優先されます。実行を引き受けるコンピュータにそのプロジェクトのローカルディレクトリがある場合、実行はそこで作業します — プロジェクトが GitHub リポジトリも指定しているかどうかは関係ありません。リポジトリが使われるのは、そのマシン上のどのローカルディレクトリもプロジェクトのコードを保持していない場合だけであり、ディレクトリの欠落や使用不可は、黙って新しい clone に置き換えられるのではなく、そのまま報告されます。ほかのコンピュータは引き続き、プロジェクトの GitHub リポジトリまたはワークスペースのリポジトリを使います。

## GitHub リポジトリの追加

プロジェクトを開き、**リソース** で「リソースを追加」を選択します。ワークスペースに紐づけ済みのリポジトリを選ぶことも、Git URL を貼り付けることもできます。ワークスペースのリポジトリは **設定 → リポジトリ** で管理します。GitHub を接続すると、同じページの **GitHub から選択** で、App が認可済みのリポジトリをインポートできます。

リポジトリは GitHub に限定されません。ランタイムがアクセスできる Git URL であれば、どれでもリポジトリリソースとして使えます。セルフホストの Multica では、**設定 → 連携 → Git ホスティング** でセルフホストの Forgejo、Gitea、GitLab も接続できます。詳細は[セルフホスト Git ホスティング](/vcs-integration)を参照してください。

プロジェクトの作成時に、**リポジトリ** で直接リポジトリを選ぶこともできます。1 つのプロジェクトには複数の GitHub リポジトリを紐づけられます。

リソースの `ref` には、以後の checkout がデフォルトで使うブランチ、タグ、またはコミットを指定できます。`default_branch_hint` はエージェントにデフォルトブランチのヒントを与えるだけで、ブランチの切り替えを強制しません。

## ローカルディレクトリの追加

ローカルディレクトリを追加する UI は Desktop でのみ提供されます。ブラウザからはコンピュータ上のフォルダを選択できないためです。

<Callout type="info">
**ローカルディレクトリは、プロジェクトにコードを与える既定の方法であり、非常口ではありません。** 実行を引き受けるコンピュータにそのプロジェクトのローカルディレクトリがあれば、実行はそれを使います。リポジトリは、コードのコピーを持たないマシンのためのフォールバックです。

フォルダは Git リポジトリである必要はありません。そうしなかった場合に何を失うかは、下の「ローカル Git を作るか、作らないか」を参照してください。
</Callout>


1. Desktop のローカルデーモンがオンラインであることを確認します。
2. プロジェクトの **リソース** を開きます。プロジェクト作成ダイアログの **ローカルディレクトリ** タブでも、プロジェクトができる前に同じ選択ができます。
3. 「ローカルディレクトリを追加」を選び、使用するフォルダを選択します。
4. 実行がそれをどう使うかを選びます — **直接**、**並行**、**共有** のいずれかで、違いは「実行がディレクトリを共有する方法」を参照してください。新しく紐づけるディレクトリは必ず **直接** から始まります。いま選んだフォルダの中で実行され、追加のディスクを消費しません。**並行** は明示的に選ぶ必要があります — 実行ごとに完全な作業コピーをあなた自身のドライブに作るからです。そのコピーがどのフォルダに置かれるかは、選ぶ前にダイアログが示します。その場で変更できますし、あとから **リソース** でディレクトリ横の鉛筆アイコンからも変更できます。

以前に紐づけたディレクトリは保存時のモードのままです — 既存の設定が知らないうちに切り替わることはありません。

ディレクトリは絶対パスで、すでに存在し、現在のデーモンが読み書きできる必要があります。次のパスは拒否されます: システムのルートとドライブのルート（`/`、`C:\`）、ホームディレクトリ自体と各ホームディレクトリの親（`/Users`、`/home`、`/root` など）、および `/etc`、`/var`、`/tmp`、`/usr`、`/opt` などのシステムディレクトリ。選択したパスがシンボリックリンクの場合は、まず実体のパスに解決してから同じルールでもう一度検証されます。直列ロックも実体のパスに対して働きます。

1 台のコンピュータで、プロジェクトは **複数の** ローカルディレクトリを紐づけられます — 互いに無関係なプレーンフォルダ 4 つでも、リポジトリ 1 つと別のドキュメントチェックアウトでも構いません。二重に紐づけられないのは、同じディレクトリ（解決済みの実体パスで判定するので、シンボリックリンクとその実体は 1 つと数えます）と、そのコンピュータにすでにあるリポジトリの 2 つ目のチェックアウトです。別々のコンピュータは、同じプロジェクトにそれぞれ自分のディレクトリを紐づけられます。

**1 回の実行が書き込むディレクトリは 1 つです。** どれになるかは 2 段階のルールに従い、サーバーで一度だけ計算されて、ランタイムと UI の両方に渡されます。タスクがリソースを明示的に指定している場合はそのリソースを使い、使えない場合は理由を添えて実行が失敗します。そうでなければ、**そのコンピュータに属するリスト内の最初のローカルディレクトリ** を使います。つまり先頭のエントリがこのマシンの既定の作業ディレクトリです — 変更するには、リストをドラッグするか、そのコンピュータのディレクトリにある移動コントロールを使ってください。残りのディレクトリは読み取り専用としてエージェントに渡され、ブリーフにも記載されるので、読むことはできても「作業してよい 2 つ目の場所」とは扱われません。

### ローカル Git を作るか、作らないか

普通のフォルダもローカルディレクトリとして使えます。紐づければ、エージェントは Git をまったく介さずにその場で編集します。そのようなフォルダを追加すると、Desktop はその中にローカル Git リポジトリを作ることを提案します — この提案は **GitHub とは何の関係もありません**。ここで作られるリポジトリは、このコンピュータ上の変更を記録するだけで、何もアップロードしません。この提案をスキップすることもでき、その行には「バージョン管理なし」のバッジが付いたままになります。

スキップして失うのは「何が起きたか」の記録です。`git diff` はなく、戻れるブランチもなく、エージェントが上書きしたファイルを復元する方法もありません。中身を気にかけているフォルダにとって、ローカルリポジトリを作ることは安い保険です。

<Callout type="warning">
既定の `in_place` モードでは、ローカルディレクトリは隔離された環境ではありません。エージェントは現在のブランチと未コミットのファイルをそのまま参照・変更し、Multica がブランチの切り替え、stash、commit、push、PR の作成を自動で行うこともありません。ワークツリーモードはこの点を変えます — 下の「実行がディレクトリを共有する方法」を参照してください。
</Callout>

## 実行がディレクトリを共有する方法

ローカルディレクトリには 3 つの実行モードがあり、リソースごとに `execution_mode` で設定します。Desktop での表示は **直接**、**並行**、**共有** で、API、CLI とこのページの以降では識別子を使います。

普通のリポジトリで重要なのは「直接」と「並行」の 2 つです。詳細の前に、そのトレードオフを示します:

| | 直接（`in_place`）— 既定 | 並行（`worktree`） |
| --- | --- | --- |
| ディスク | 追加のディスクを消費しません | 実行ごとに完全な作業コピー、およびそのコピー自身の依存関係を、あなたのプロジェクトのディスク上に持ちます |
| 並行性 | そのディレクトリでは一度に 1 実行。後から来た実行はキューに入ります | 同じディレクトリで任意の数の実行 |
| 失敗したときの現場 | あなた自身のディレクトリ — エージェントは作業しながらあなたの作業コピーを編集し、残したものはあなたがすでにいるその場所にあります | リポジトリの隣にある、あなたが開ける作業コピー。あなた自身の作業コピーは決して変更されません |
| 誰が片付けるか | 片付けるものがありません | 既定ではあなたです。自動クリーンアップはオプトインで、マージ済みでクリーンなコピーだけを削除します |
| リスク | エージェントとあなたのエディタが同じツリーに書き込みます | 実行同士が互いに隔離されます |

**既定は「直接」** で、最も安い選択です。追加のディスクも、片付けるものもありません。並行は、本当に複数のタスクを同時に抱えるディレクトリのためのものです — あなた自身のマシン上のディスクと、あなたが片付ける責任を負う作業コピーと引き換えに、並行性を得ます。

### `in_place`（既定）— 「直接」

エージェントはあなたのディレクトリで直接作業し、実行は一度に 1 つずつ進みます。2 つの実行が同じ実体のディレクトリを使う場合、後から来た実行は `waiting_local_directory` に入り、先の実行がディレクトリを解放してから続行します。異なるシンボリックリンク経由で同じディレクトリに到達する 2 つのパスも、同じように直列化されます。

待機中にディレクトリが変更されることはありません。待機中の実行はキャンセルできます。キャンセルしなければ、ディレクトリが使えるようになるまで待ち続けます。

### `worktree` — 「並行」

各実行が、あなたのリポジトリの独立した [git ワークツリー](https://git-scm.com/docs/git-worktree) を受け取ります。ワークツリーは **あなた自身のドライブ上、リポジトリの隣** に作成されます — 既定では `<repo>.multica-worktrees/<run>` です。**同じディレクトリに対する実行は並行して進み、待機は発生しません**。どの実行もあなたの作業コピーには書き込みません。

コピーはリポジトリの内部ではなく隣に置かれるため、あなた自身の `git status` に現れず、`.gitignore` に何かを足す必要もありません。Multica のワークスペースではなくあなたのディスクに置く理由はひとつです。実行が失敗したとき、そのコピーはどこまで進んだかを示す唯一の記録であり、あなたが同意した覚えのないクリーンアップ周期で消えてよいものではないからです。その代わり、その容量はあなたのものです — 後述の「作業コピーを片付ける」を参照してください。

このモードには、コミットが 1 つ以上ある git リポジトリであることが必要です。そうでない場合、実行は黙って直列実行に戻るのではなく、明示的なエラーで失敗します。そのマシンのランタイムも、このモードを実装している必要があります。ランタイムは接続時にその能力を宣言し、Multica はバージョン番号ではなくこの宣言で判定します — 開発ビルドは、実装がまったくないまま十分に新しく見えるバージョン文字列を持ちうるからです。この宣言は 2 回検証されます。そのマシンのランタイムが能力を宣言していない間、リソースの保存は拒否され、そのマシンのアプリを更新するよう促されます。さらに各実行は実際にそれを受け取ったランタイムに対して再度検証されます — つまりリソース保存後にダウングレードされたマシンでは、実行が黙ってその場で処理されるのではなく、理由付きでキャンセルされます。`worktree` を選ぶことは隔離を求めることであり、代わりに作業コピーを書き換えることがフォールバックになることはありません。

エージェントが見るもの、あなたが受け取るもの:

- **エージェントは `HEAD` ではなく、あなたが今見ている状態から開始します。** 未コミットの変更と未追跡ファイルがワークツリーに再現されるため、すでに手元にないコードをレビューすることはありません。あなた自身の作業コピー、インデックス、stash リストが変更されることはありません。その状態を忠実に再現できない場合 — 再現の上限（2000 ファイル / 200 MiB）を超える未追跡コンテンツがある場合を含む — 実行は、見覚えのないツリーから開始する代わりに失敗します。通常の対処法は、まだ無視されていないビルド成果物を gitignore に加えるか削除することです。
- **成果物はあなたのリポジトリ内のブランチ**で、実行ごとではなくタスクごとに 1 本、`agent/<agent>/<issue>`（チャットなら `agent/<agent>/chat-<session>`）という名前が付きます。実行の「実行詳細」パネルにブランチ名が表示され（コピーも可能）、`git branch` でも見つけられます。`git log` / `git diff` でレビューし、マージするか cherry-pick するかは自分で決めます。Multica が代わりにマージすることはありません。途中で失敗した実行もブランチを報告します。エージェントが作った分はすでにコミットされているからです。
- **続きのコメントは前回の続きから始まります。** 同じタスクへの次のコメントはそのブランチを再びチェックアウトするので、エージェントは直前に納品した成果の上で作業します。`HEAD` からやり直して前回の変更が別ブランチに取り残されることはありません。再適用されるのは前回以降にあなたが自分のディレクトリで変えた分だけです — それ以外はブランチがすでに持っています。ブランチをマージすれば、次の実行はまたあなたの `HEAD` から始まります。同じタスクで 2 つの実行が重なった場合、あとの実行は前の実行の成果から `agent/<agent>/<issue>-<task>` に分岐します。git では 1 つのブランチに 1 つの worktree しか持てないためです。
- **あなたの変更がエージェントの成果と衝突したら、エージェントが解決します。** エージェントが書き換えたのと同じ行をあなたが書き換えた場合、git はどちらが正しいか決められません。その実行は衝突したままのワークツリーで始まり、何より先にマージを終わらせるよう指示されます（そのワークツリーで `git status` を実行すると未マージのファイルが並びます）。未マージのファイルが残ったままの実行は何も納品しません。実行は失敗し、ワークツリーは保持され、次の実行が同じ変更をもう一度提示するので、あなたの変更が黙って消えることはありません。
- **Multica のものだと確認できたブランチだけを引き継ぎます。** 引き継ぐかどうかは名前ではなく所有記録で決まります。記録にはどの対話のものかに加えて、そのブランチが最後に置かれたコミットも書かれています。あなたが自分で作った、たまたま `agent/<agent>/<issue>` という名前のブランチが、チェックアウトされることも、追記されることも、前回の成果として読まれることもありません。記録されたコミットをもう含まないブランチも同様なので、Multica のブランチを削除して同名のものを作り直したり、別の履歴へ force-move したりしても安全です。その場合、実行は `agent/<agent>/<issue>-<id>` を使います。納品済みブランチの上にコミットするのは通常の使い方で、引き継ぎはそのまま続き、あなたのコミットは次の実行にそのまま含まれます。各ブランチはそれ自身のベースラインコミットから始まります。最初の実行が開始した時点のツリーを示すもので、あとでブランチを識別するのはこのコミットであり、`git diff <baseline>..<branch>` はちょうどエージェントの変更になります。ブランチを記録できなかった実行 — 途中で失敗した、記録の書き込みに失敗した、あるいはあなたの変更をブランチに取り込んだコミットより前にワークツリーをリセットした場合 — は失敗として報告されワークツリーを残します。以降の実行は自分のものだと証明できないブランチを引き継がず、新しいブランチから始めます。
- **黙って失われるものはありません。** エージェントが未コミットのまま残した変更は、ワークツリーが削除される前にそのブランチへコミットされます。**実行が途中で失敗した場合も同様です。** ごくまれにそのコミット自体が実行できない場合 — 例えば `commit.gpgSign` が有効で、ランタイムが署名鍵を利用できないリポジトリ — ワークツリーは削除されずに意図的に保持され、実行は失敗として報告されます。あなたのリポジトリで `git worktree list` を実行すると、その変更を保持しているディレクトリが表示されます。
- **何も変更しなかった実行は、何も残しません。** そのブランチは `git branch` に空の項目として残らず、削除されます。ただし、それまでの実行の成果を持つタスクのブランチは常に残ります。

あなたのリポジトリに残るのは 2 つ、ブランチと、ブランチごとの隠しref（`refs/multica/local-state/` 配下）です。後者はそのブランチの所有者と、最後に引き継いだ時点のあなたのディレクトリの内容を記録します。隠しrefは `git branch` には現れません。`git for-each-ref refs/multica` で一覧できます。Multica はブランチと一緒に削除し、あなたが自分で消したブランチのrefは、そのリポジトリで次の実行が始まるときに片付けます。`git for-each-ref --format='%(refname)' refs/multica | xargs -n1 git update-ref -d` で一括削除もできます。

### `shared` — 「共有」

実行はあなたのディレクトリ内で同時に、**ロックをまったくかけずに** 進みます。共有モードは、1 つのディレクトリに複数のリポジトリや複数の独立した作業が入っている場合のためのものです。そこでは各タスクが、Multica にフォルダの直列化を任せるのではなく、リポジトリごとの自分のワークツリーで自己隔離します。何もコピーされず、何も待ちません。ロックもかからないため、同じツリーに実際に触れる 2 つの実行は互いに踏み合うことがあります。そのディレクトリ内の作業が本当に独立している場合にのみ選んでください。並行と違い、git リポジトリも、ブランチとしての成果の返却も必要ありません — その部分はあなた自身の取り決めです。

### 作業コピーを片付ける

正常に終了した実行は自分の作業コピーを削除します。残るのは実行を **完了できなかった** もの — 未解決のマージ、失敗したコミット、停止したマシン — で、それらは意図的にディスク上に残ります。その実行の状態を後から確認できる唯一の場所だからです。

残ったコピーの自動クリーンアップは、プロジェクトではなく **コンピュータ側の設定** です。ディスクはコンピュータの属性だからです。設定は Desktop のデーモン設定にあり、**既定はオフ** です。コピーの一覧と各コピーがどう扱われるかは、スイッチのオン・オフに関わらず表示されます。有効にする前にポリシーの判定を読めるようにするためです。

スイッチをオンにしても、コピーが削除されるのは次の **すべて** を満たす場合だけです:

1. Multica が作成したものであること — あなたが `git worktree add` で作ったワークツリーは決して触りません;
2. どの実行にも使われていないこと;
3. 最後の実行から、設定した期間（既定は 14 日）より長く経っていること;
4. その中の `git status --porcelain` が空であること — `.gitignore` の対象（`node_modules` など）は数えません;
5. その作業がすでにトランクブランチに入っていること —— ブランチがトランクに含まれているか、変更が squash されて取り込まれているか。squash マージは作業を新しいコミットに書き換えるため、ブランチ自体がトランクの祖先になることはありません。祖先ではなく内容で比べることで、squash 運用のリポジトリでもこの条件に到達できます。「リモートブランチが消えている」「プルリクエストがマージ済み」は意図的に採用していません。前者はマージ後に削除されたブランチと一度も push されていないブランチを区別できず、後者は自分のディスクの掃除をネットワークと GitHub に依存させてしまうからです。

ひとつでも満たさなければコピーは保持され、設定画面がどの条件かを示します。重要なのは 4 番です。ブランチがマージ済みであることは、ディレクトリ内に未コミットのまま何が残っているかを何も語りません。そしてそれこそが、失敗した実行が残すものです。削除は必ず `git worktree remove` を通すので、リポジトリに古い `.git/worktrees` エントリが残って同じ名前が使えなくなることはありません。

その一覧から 1 つだけ片付けることもできます。これは「どのコピーか」を指定するものであって「ルールを無視する」ことではありません — 同じ 5 つの条件が、その時点のディレクトリに対して再確認されます。

<Callout type="warn">
**セルフホスト運用者向け:** このモードの分離はサーバー側で強制されます（リソース保存時と、ランタイムが各実行を取得する時点の二重チェック）。そのため、ランタイムをいつダウングレードしても検出されます。検出できない唯一の組み合わせは、このモードを実装していないランタイムが接続されたまま、サーバーをこの機能より前のビルドへロールバックすることです — 古いサーバーにはこのゲートがなく、そうしたランタイムは `execution_mode` を無視して実行を元のディレクトリで直接処理してしまいます。`worktree` リソースが存在する間は、対象マシンのランタイムがすべて最新でない限り、サーバーをこのリリースより前へロールバックしないでください。
</Callout>

<Callout type="info">
ワークツリーモードは git リポジトリを対象とします。git 管理外の通常のディレクトリは引き続き直列実行です — それが `in_place` の役割です。
</Callout>

## 何も紐づけていないとき: 共有セッションフォルダ

マシン上にローカルディレクトリもリポジトリもない実行には、作業するコードがなく、ファイルを置く場所だけがあります。そのような実行に毎回新しいタスクディレクトリが与えられることはありません。1 つの会話の各ターンが同じフォルダを使うので、1 つのスレッドで 20 回質問しても 20 個分のフォルダが散らかることはありません。

フォルダはエージェントを実行しているコンピュータ上の、デーモンのワークスペースルート配下に、`.sessions/<workspace-id>/sessions/<conversation-id>` として置かれます。ワークスペースルートの既定は `~/multica_workspaces`（名前付きプロファイルでは `~/multica_workspaces_<profile>`）で、`MULTICA_WORKSPACES_ROOT` で変更できます。

このフォルダは Multica のものなので、自動的にクリーンアップされます。**既定でオン** であり、あなた自身のドライブ上の並行な作業コピーとは逆です。ある会話のフォルダが削除されるのは、Multica が作成したものであり、どの実行も使っておらず、保持期間（既定は 14 日）を過ぎてアイドル状態になっている場合だけです。Desktop のデーモン設定には、このフォルダ、そのサイズ、そして各会話が「なぜ保持され、なぜ消されるか」が表示されます。そこから 1 つの会話を片付けることもできます。スキャンがこのルートの外へ出ることはありません。あなたのディレクトリや、リポジトリの隣の作業コピーが候補になることはありません。

## サーバーが実行の置き場所を決められないとき

実行がどのディレクトリに書き込むかは、ランタイムがその実行を引き受ける前に、サーバーで一度だけ決定されます — そしてランタイムは自分で選び直すのではなく、その決定を検証します。答えを導けない場合、実行は別のディレクトリや新しいリモート checkout にフォールバックするのではなく、コードを付けて失敗します: `daemon_cannot_run_mode`、`unknown_execution_mode`、`malformed_resource`、`pinned_resource_not_found`、`pinned_resource_other_machine`、`pinned_resource_unusable`。各コードとその次の一歩は、[トラブルシューティング](/troubleshooting#コードソースの失敗コード)に一覧されています。

古いランタイムは影響を受けません。サーバーは、引き受けるランタイムが処理できると宣言した範囲にリソース一覧を絞り込むため、複数のローカルディレクトリや新しい作業コピーの置き場所より前のランタイムは、以前とまったく同じリソースを受け取ります — **アップグレードは不要** で、その実行の挙動もこれまでどおりです。

## 実行中に書き込まれるもの

エージェントによるコードの変更のほかに、ランタイムは、現在の AI コーディングツールが必要とする指示ファイルと `.multica/project/resources.json` を作業ディレクトリに書き込むことがあります。Multica は実行が終わると自分のファイルを改めて削除するため、「直接」の実行はエージェントの変更を別にすればフォルダを元のまま返し、「並行」の実行はあなたのフォルダに一切書き込まず、「共有」の実行は Multica のファイルをその中に残しません。

Multica が実行環境をクリーンアップするとき、紐づけたローカルディレクトリを削除することはありません。エージェントによるこのディレクトリへの変更は、あなたがターミナルで AI コーディングツールを直接実行したときの変更と同じ性質のものであり、同じようにレビューが必要です。

## CLI でリソースを管理する

```bash
# プロジェクト作成時にリポジトリを紐づける
multica project create \
  --title "Agent UX" \
  --repo https://github.com/multica-ai/multica

# リソースの一覧表示と追加
multica project resource list <project-id>
multica project resource add <project-id> \
  --type github_repo \
  --url https://github.com/multica-ai/multica \
  --ref main

# 特定のデーモン上のローカルディレクトリを紐づける
multica project resource add <project-id> \
  --type local_directory \
  --local-path /absolute/path/to/repo \
  --daemon-id <daemon-id>

# ローカル git リポジトリを紐づけ、実行を各自のワークツリーで並行処理する
multica project resource add <project-id> \
  --type local_directory \
  --local-path /absolute/path/to/repo \
  --daemon-id <daemon-id> \
  --execution-mode worktree

# 既存のローカルディレクトリのモードを切り替える
multica project resource update <project-id> <resource-id> --execution-mode worktree
multica project resource update <project-id> <resource-id> --execution-mode in_place


# リソースを削除する
multica project resource remove <project-id> <resource-id>
```

リソースの変更は、その後に作成される実行に反映されます。すでに終了した実行の記録が書き換えられることはありません。
