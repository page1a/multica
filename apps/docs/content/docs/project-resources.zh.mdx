[项目](/projects)资源告诉智能体这组工作会用到哪些代码，以及在哪里执行。资源会持续关联在项目上，不必在每条任务中重复粘贴仓库地址或本地路径。

目前支持两种资源：

| 资源 | 适用场景 | 执行位置 |
|---|---|---|
| **GitHub 仓库** | 团队共享的代码库，希望由运行时管理 checkout | 运行时管理的工作目录 |
| **本地目录** | 已经存在的 checkout、很大的仓库，或需要直接查看本地改动 | 指定电脑上的原目录 |

## 六种形态对照

几乎所有用法都落在这六种里。在第一列找到你的情况，下面各节再解释其中的零件。

| | 什么情况 | 绑什么 | 干活目录在哪 | 谁的盘、谁会清它 | 并发 | 改动怎么交回你 |
| --- | --- | --- | --- | --- | --- | --- |
| **A** | 本地 Git 仓库，有没有远端都行 —— **默认形态** | 本地目录 · **原地** | **你的目录本身** | 不额外占空间 | 同一目录一次一个，后到的排队 | 直接改你的工作副本，你自己 `git diff`、自己撤销 |
| **B** | 本地 Git 仓库，而且这个目录确实要多任务同时跑 | 本地目录 · **并行** | **你仓库同级的一份工作副本目录** —— 默认是 `<仓库>.multica-worktrees/<运行>` | **你自己的盘。** 默认谁都不清；只有打开自动清理后，才会删掉已合并、超过 N 天、且没有未提交改动的副本 | 同一目录上的运行并发执行 | 分支已经在你自己的仓库里，现场也留在你能打开的目录里 |
| **C** | 本地纯文件夹，完全没有 Git | 本地目录 · **原地** | **你的目录本身** | 不额外占空间 | 一次一个，后到的排队 | 直接改 —— 没有 diff，也**不能回退** |
| **D** | 一个目录里装了好几个仓库、好几摊活 | 本地目录 · **共享** | **你的目录本身**，不加锁 | 不额外占空间 | 并发，但不加锁，两个运行可能互相踩 | 直接改 |
| **E** | 云端项目，或这台电脑上根本没有这份代码 | GitHub 仓库 | Multica 工作区里的一份 checkout | Multica 的盘，按正常清理周期回收 | 天然并发 | 一条分支推到远端 |
| **F** | 什么都没绑，只是随手问答 | 什么都不绑 | **一个公用的会话文件夹**（按会话归档，不是每次运行新建一个） | Multica 的盘，而且占得很少 | — | 产物留在那个文件夹下、本次会话自己的目录里 |

## 资源进入执行的方式

当智能体处理项目内的任务时，Multica 会把项目名称、项目描述和资源列表加入执行上下文，并把资源列表写入 `.multica/project/resources.json` —— 它可能落在干活目录里，也可能落在守护进程自己的单次运行文件夹里，取决于运行在哪里发生。见下面的"执行期间写入的内容"。

工作区关联的仓库列表始终包含在执行上下文中。项目关联的仓库在此基础上指明这组工作使用的代码和默认 ref。

本地目录只对绑定它的守护进程有效，而且它优先于仓库。领取这次运行的电脑上有这个项目的本地目录时，运行就在那个目录里干活 —— 项目同时配了 GitHub 仓库也一样。只有当这台机器上没有任何本地目录持有这个项目的代码时，才会去用仓库；目录缺失或不可用会如实报错，而不是悄悄换成一份新的 clone。其他电脑仍使用项目中的 GitHub 仓库或工作区仓库。

## 添加 GitHub 仓库

打开项目，在 **资源** 中选择"添加资源"。可以选择已关联到工作区的仓库，也可以粘贴 Git URL。工作区仓库在 **设置 → 代码仓库** 中维护；连接 GitHub 后，可在同一页面通过 **从 GitHub 选择** 导入 App 已授权的仓库。

仓库不限于 GitHub：任何运行时能访问的 Git URL 都可以作为仓库资源。自部署的 Multica 还可以在 **设置 → 集成 → Git 代码托管** 连接自托管的 Forgejo、Gitea 或 GitLab，见[自托管 Git 代码托管](/vcs-integration)。

创建项目时，也可以直接在 **Repos** 中选择仓库。一个项目可以关联多个 GitHub 仓库。

资源中的 `ref` 可以指定后续 checkout 默认使用的分支、tag 或 commit。`default_branch_hint` 只向智能体提供默认分支提示，不会强制切换分支。

## 添加本地目录

添加本地目录的界面只在 Desktop 中提供，因为浏览器不能选择电脑上的文件夹。

<Callout type="info">
**本地目录是给项目配代码的默认方式，不是逃生舱。** 领取运行的电脑上有这个项目的本地目录时，运行就用它；仓库是那些本机没有这份代码的机器的兜底。

文件夹不必是 Git 仓库。不建 Git 会少掉什么，见下面的"建不建本地 Git"。
</Callout>


1. 确认 Desktop 的本地守护进程在线。
2. 打开项目的 **资源**，或者创建项目对话框里的 **本地目录** 标签页 —— 项目还没建出来时也能做同样的选择。
3. 选择"添加本地目录"，再选择要使用的文件夹。
4. 选择运行如何使用它 —— **原地**、**并行** 还是 **共享**，区别见"运行如何共享这个目录"。新关联的目录一律从 **原地** 开始：运行就在你刚选的文件夹里干活，不额外占磁盘。**并行** 必须由你明确选择，因为它会为每次运行在你自己的盘上建一份完整工作副本；在你点下去之前，对话框就会写明这些副本落在哪个目录。当场可以改，之后也可以在 **资源** 里点目录旁边的铅笔图标改。

之前关联好的目录仍然保持保存时的模式 —— 已有的配置不会在你不知情的情况下被切换。

目录必须是绝对路径，已经存在，并且当前守护进程可以读取和写入。以下路径会被拒绝：系统根目录和盘符根（`/`、`C:\`）、用户主目录本身及各主目录的上级（如 `/Users`、`/home`、`/root`），以及 `/etc`、`/var`、`/tmp`、`/usr`、`/opt` 等系统目录。如果所选路径是符号链接，会先解析为真实路径再按同样的规则校验一次，串行锁也按真实路径生效。

一个项目在同一台电脑上可以关联 **多个** 本地目录 —— 四个互不相关的纯文件夹，或者一个仓库加一份单独的文档检出。不能重复关联的是同一个目录（按解析后的真实路径判断，所以符号链接和它指向的目标算同一个），以及这台电脑上同一个仓库的第二份检出。不同电脑可以各自为同一个项目关联自己的目录。

**一次运行只写一个目录。** 用哪一个遵循只有两步的规则，由服务端算一次、同时交给运行时和界面：任务显式指定了某个资源，就用那个资源，用不了就带原因失败；否则取 **列表里这台电脑的第一条本地目录**。所以排第一的那条就是这台电脑的默认工作目录 —— 拖动列表，或用这台电脑目录上的移动按钮来改。其余目录以只读方式交给智能体，并写进它的简报，让它能读、但不会当成第二个可以动手的地方。

### 建不建本地 Git

纯文件夹也能当本地目录：绑上去，智能体就在原地改，全程不涉及 Git。添加这种文件夹时，Desktop 会提议在里面建一个本地 Git 仓库 —— 这个提议**和 GitHub 没有关系**：在这里建仓库只是把这台电脑上的改动记下来，不会上传任何东西。你可以跳过，这一行会一直带着"无版本控制"的标记。

跳过少掉的是"发生过什么"的记录：没有 `git diff`，没有可以退回去的分支，也没有办法把智能体覆盖掉的文件找回来。对一个你在意内容的文件夹来说，建这个本地仓库是便宜的保险。

<Callout type="warning">
在默认的 `in_place` 模式下，本地目录不是隔离环境：智能体会直接看到并修改当前分支和未提交的文件，Multica 也不会自动切换分支、stash、commit、push 或创建 PR。worktree 模式会改变这一点 —— 见下面的“运行如何共享这个目录”。
</Callout>

## 运行如何共享这个目录

本地目录有三种执行模式，按资源逐个设置。Desktop 里显示为 **原地**、**并行** 和 **共享**；API、CLI 和本页其余部分都使用标识符。

对普通仓库来说，真正要选的是原地和并行，取舍先摆在这里：

| | 原地（`in_place`）—— 默认 | 并行（`worktree`） |
| --- | --- | --- |
| 磁盘 | 不额外占空间 | 每次运行一份完整工作副本，外加这份副本自己的依赖，占的是你项目的盘 |
| 并发 | 同一目录一次一个，后到的排队 | 同一目录任意并发 |
| 现场 | 就是你的目录 —— 智能体一边干就在改你的工作副本，留下的东西也就在你手边 | 留在你仓库旁边那份你能打开的工作副本里；你自己的工作副本不会被碰 |
| 谁来清 | 没有东西要清 | 默认你自己清；自动清理要主动打开，且只删已合并、干净的副本 |
| 风险 | 智能体和你的编辑器改的是同一棵树 | 各次运行互相隔离 |

**默认是原地**，也是最省的那个：不占额外磁盘，也没有东西要清。并行是给那些确实要同时跑好几个运行的目录用的 —— 它用你自己机器上的磁盘、以及一份由你负责清理的工作副本，换来并发。

### `in_place`（默认）—— “原地”

智能体直接在你的目录里工作，同一时间只进行一次运行。两次运行使用同一个真实目录时，后到的运行进入 `waiting_local_directory`，等前一次释放目录后继续。两个路径经不同符号链接指向同一目录时，同样串行。

等待不会修改目录。等待中的运行可以取消，否则会一直等到目录可用。

### `worktree` —— “并行”

每次运行拿到你仓库的一个独立 [git worktree](https://git-scm.com/docs/git-worktree)，**建在你自己盘上、仓库旁边** —— 默认是 `<仓库>.multica-worktrees/<运行>`。**同一目录上的运行并发执行，谁都不用排队**，并且都不会写你的工作副本。

副本放在仓库旁边而不是仓库内部，所以它们不会出现在你自己的 `git status` 里，也不需要往 `.gitignore` 加任何东西。它们落在你的盘上而不是 Multica 的工作区，只有一个理由：运行失败时，那份副本是它到底走到哪一步的唯一记录，不该按一个你从没同意过的清理周期消失。代价是这份空间是你的 —— 见下面的"清理工作副本"。

要求这个目录是一个至少有一次提交的 git 仓库。如果不是，运行会明确报错，而不是悄悄退回串行。那台机器上的运行时也必须实现了该模式。运行时在连接时会声明这项能力，Multica 判断的是这个声明而不是版本号 —— 一个开发构建完全可能带着看起来足够新的版本号，却根本没有对应的实现。这个声明会被检查两次：只要那台机器的运行时没有声明该能力，保存资源就会被拒绝，并提示去升级那台机器上的 App；每次运行在被真正领取时还会再按领取它的运行时检查一次 —— 所以资源保存之后才降级的机器，其运行会被带原因取消，而不是悄悄原地跑掉。选择 `worktree` 就是在要求隔离，把它换成“直接改你的工作副本”永远不是兜底方案。

智能体看到什么、你拿回什么：

- **智能体从你眼前的状态开始，而不是从 `HEAD` 开始。** 你未提交的改动和未跟踪的文件会被回放进 worktree，所以它不会去 review 一份你已经不用的代码。你自己的工作副本、暂存区和 stash 列表都不会被动到。如果这个状态无法忠实还原 —— 包括未跟踪内容超出回放上限（2000 个文件 / 200 MiB）—— 运行会直接失败，而不是从一棵你认不出来的树开始。通常的解决办法是把还没被忽略的构建产物加进 gitignore 或清理掉。
- **结果是你仓库里的一个分支**，按任务而不是按每次执行来分：`agent/<agent>/<issue>`（chat 则是 `agent/<agent>/chat-<session>`）。本次运行的**详情**面板里会显示分支名（可直接复制），也可以用 `git branch` 找到它。用 `git log` / `git diff` review，然后自己决定 merge 还是 cherry-pick。Multica 不会替你合并。中途失败的运行同样会报告它的分支，因为它已经把智能体做出来的部分提交进去了。
- **后续对话接着上一轮继续。** 同一个任务的下一条评论会重新 check out 这个分支，智能体站在自己刚交付的成果上继续做，而不是从 `HEAD` 重新开始、把上一轮的改动落在另一个分支上。只有你在上一轮之后改动的部分会被重放上去 —— 其余部分分支里已经有了。把分支 merge 掉之后，下一轮又会从你的 `HEAD` 重新开始。同一个任务上有两次执行重叠时，后一个会从前一个的成果分叉到 `agent/<agent>/<issue>-<task>`，因为 git 规定一个分支只能有一棵 worktree。
- **你的改动和智能体的成果冲突时，由智能体来解决。** 如果你重写了智能体也重写过的那几行，git 无法判断谁对，这一轮就会在一棵带冲突的 worktree 上启动，并被要求先把 merge 做完（在那棵 worktree 里 `git status` 会列出未合并的文件）。只要还有文件没合完，这一轮就什么都不交付：运行失败、worktree 保留，下一轮会再次把同样的改动送上来，所以你的修改不会被悄悄丢掉。
- **只有 Multica 自己的分支才会被续接。** 是否续接由归属记录决定，而不是看名字：记录里既写了属于哪个会话，也写了这条分支当时停在哪个 commit。你自己建的、恰好叫 `agent/<agent>/<issue>` 的分支永远不会被 check out、被追加提交，也不会被当成上一轮的成果读取；已经不包含记录中那个 commit 的分支同样如此 —— 所以你把 Multica 的分支删掉再自己建一条同名的，或者把它 force-move 到别的历史上，都是安全的，运行会改用 `agent/<agent>/<issue>-<id>`。在已交付的分支上继续提交则是正常用法，续接照常，你的提交下一轮就在那里。每条分支还会以一个属于自己的 baseline commit 开头，标记第一轮开始时的目录状态 —— 后续正是靠这个 commit 来辨认这条分支，同时 `git diff <baseline>..<branch>` 恰好就是智能体做的改动。如果某一轮没能记录它的分支 —— 中途失败、记录写不进去，或者把 worktree reset 到了「把你的改动带进分支的那个 commit」之前 —— 这一轮会报失败并保留 worktree，后续几轮会另起一条分支，而不是去续接一条无法证明归属的分支。
- **不会静默丢东西。** 智能体留下的未提交改动，会在 worktree 被移除前提交到那个分支上，**运行中途失败时同样如此**。极少数情况下连这次提交都做不了 —— 例如仓库开了 `commit.gpgSign` 而运行时拿不到签名密钥 —— worktree 会被刻意保留而不是删除，运行标记为失败，并且在你仓库里执行 `git worktree list` 就能看到存放这些改动的目录。
- **没有产生改动的运行不留下任何东西。** 它的分支会被删除，而不是作为一个空条目留在 `git branch` 里；但如果这是承载了之前几轮成果的任务分支，它一定会保留。

留在你仓库里的有两样东西：分支，以及每条分支对应的一个隐藏 ref（在 `refs/multica/local-state/` 下），记录这条分支归谁所有、以及上次续接时你目录里的内容。隐藏 ref 不会出现在 `git branch` 里，可以用 `git for-each-ref refs/multica` 查看。Multica 删除分支时会一并删掉它；你自己删掉的分支所对应的 ref，会在下一次该仓库上有运行开始时被清理 —— 也可以用 `git for-each-ref --format='%(refname)' refs/multica | xargs -n1 git update-ref -d` 一次性清掉。

### `shared` —— “共享”

运行在你的目录里同时执行，**完全不加锁**。共享模式是给"一个目录里装了好几个仓库、好几摊活"的目录用的：每个任务靠自己的 per-repo worktree 自我隔离，而不是靠 Multica 把这个文件夹串行化。不复制、不排队，也不上锁，所以两个真的碰到同一棵树的运行可能互相踩。只有确认这个目录里的活彼此独立时才选它。和并行不同，它不需要 git 仓库，也不负责把改动以分支形式交回 —— 那部分由你自己的约定负责。

### 清理工作副本

正常跑完的运行会自己移除工作副本。留下来的那些，是运行 **没能** 跑完的 —— 没解完的冲突、提交失败、机器中途挂了 —— 它们是故意留在盘上的：那是这次运行的状态唯一还能被查看的地方。

自动清理这些残留是**电脑上的设置**，不是项目上的设置，因为磁盘是电脑的属性。它在 Desktop 的守护进程设置里，**默认关闭**。无论开关是开是关，副本列表和每一条会被怎么处理都照常显示，这样你可以先读懂这套规则，再决定要不要同意。

开关打开后，只有 **同时** 满足下面全部条件，副本才会被删除：

1. 它是 Multica 创建的 —— 你自己用 `git worktree add` 建的永远不会被碰；
2. 没有运行正在使用它；
3. 最后一次运行结束已超过你设置的天数（默认 14 天）；
4. 里面的 `git status --porcelain` 为空 —— 被 `.gitignore` 覆盖的文件（比如 `node_modules`）不计入；
5. 它的工作已经在主干分支里 —— 分支本身被包含在主干里，或者它的改动已被 squash 合入。squash 合并会把工作改写成一个新 commit，分支本身永远不会成为主干的祖先；按内容而不是按祖先来比，这一条在 squash 工作流的仓库里才有可能成立。「远端分支已删」和「PR 已合并」是特意**不**采信的：前者分不清"合并后删掉的分支"和"从来没推过的分支"，后者会让清理自己电脑的磁盘依赖网络和 GitHub。

其中任何一条不成立都会保留这份副本，设置页会写明是哪一条。第 4 条最重要：分支已合并，完全说明不了目录里还有什么没提交的东西，而那恰恰是失败的运行留下的东西。删除一律走 `git worktree remove`，所以你的仓库里不会残留一条过期的 `.git/worktrees` 记录、让同名目录以后建不出来。

你也可以在那个列表里单独清理某一份。这表示的是"清哪一份"，而不是"忽略规则" —— 同样这五条会按目录当下的状态重新检查一遍。

<Callout type="warn">
**自托管运维注意：** 该模式的隔离由服务端强制（保存资源时检查一次，运行时每次领取执行时再检查一次），所以无论何时降级运行时都会被拦住。唯一拦不住的组合是：把服务端回滚到本功能之前的版本，同时还连着没有实现该模式的运行时 —— 旧服务端没有这道门禁，而这样的运行时会忽略 `execution_mode`、直接在原目录里执行。只要还存在 `worktree` 资源，就不要把服务端回滚到本版本之前，除非那些机器上的运行时全部升级到位。
</Callout>

<Callout type="info">
worktree 模式面向 git 仓库。普通的非 git 目录仍然串行执行 —— 这正是 `in_place` 的用途。
</Callout>

## 什么都没绑时：公用会话文件夹

一台机器上既没有本地目录、也没有仓库的运行，没有代码可以干活，只有一个放文件的地方。它不会每次新建一个任务目录：一段对话的每一轮都用同一个文件夹，所以同一串里问二十次不会留下二十个目录。

文件夹在跑智能体的那台电脑上，位于守护进程的工作区根目录之下：`.sessions/<工作区 id>/sessions/<会话 id>`。工作区根目录默认是 `~/multica_workspaces`（命名 profile 是 `~/multica_workspaces_<profile>`），可以用 `MULTICA_WORKSPACES_ROOT` 改。

这个文件夹是 Multica 自己的，所以会自动清理：**默认打开**，这一点和落在你自己盘上的并行工作副本相反。只有同时满足"是 Multica 创建的""没有运行正在用它""闲置已超过保留窗口（默认 14 天）"，某个会话的文件夹才会被删除。Desktop 的守护进程设置里能看到这个文件夹、它的占用，以及每个会话"为什么会被清、为什么被留下"；也可以在那里单独清理某个会话。扫描不会走出这个根目录：你自己的目录、仓库旁边的工作副本，永远不会成为候选。

## 服务端算不出落点时

一次运行写哪个目录，由服务端在运行时领取之前算一次，运行时只校验这个结论、不再自己挑。算不出来时，运行会带失败码结束，而不是退到另一个目录或重新拉一份远端代码：`daemon_cannot_run_mode`、`unknown_execution_mode`、`malformed_resource`、`pinned_resource_not_found`、`pinned_resource_other_machine`、`pinned_resource_unusable`。每个失败码的含义与下一步动作见[故障排查](/troubleshooting#代码来源失败码)。

旧版运行时不受影响。服务端下发的资源集合会收窄到"领取它的运行时声明自己能处理"的范围，所以早于"多本地目录"或"工作副本新落点"的运行时，收到的资源和以前完全一样 —— **无需升级**，它的运行行为也和过去完全一致。

## 执行期间写入的内容

除了智能体产生的代码改动，运行时还可能在干活目录里写入当前 AI 编程工具所需的说明文件，以及 `.multica/project/resources.json`。运行结束时 Multica 会把自己写的文件收回去：所以"原地"会把你的文件夹原样还给你（只剩下智能体的改动），"并行"根本不往你的文件夹里写，"共享"则不让 Multica 的文件落进去。

Multica 清理执行环境时不会删除关联的本地目录。智能体对该目录的改动，与你在终端中直接运行 AI 编程工具的改动性质相同，需要同样的审查。

## 使用 CLI 管理资源

```bash
# 创建项目时关联仓库
multica project create \
 --title "Agent UX" \
 --repo https://github.com/multica-ai/multica

# 查看和添加资源
multica project resource list <project-id>
multica project resource add <project-id> \
 --type github_repo \
 --url https://github.com/multica-ai/multica \
 --ref main

# 关联指定守护进程上的本地目录
multica project resource add <project-id> \
 --type local_directory \
 --local-path /absolute/path/to/repo \
 --daemon-id <daemon-id>

# 关联一个本地 git 仓库，并让每次运行在各自的 worktree 中并发执行
multica project resource add <project-id> \
 --type local_directory \
 --local-path /absolute/path/to/repo \
 --daemon-id <daemon-id> \
 --execution-mode worktree

# 为已有的本地目录切换模式
multica project resource update <project-id> <resource-id> --execution-mode worktree
multica project resource update <project-id> <resource-id> --execution-mode in_place

# 移除资源
multica project resource remove <project-id> <resource-id>
```

资源变更会影响之后创建的运行，不会改写已经结束的执行记录。
