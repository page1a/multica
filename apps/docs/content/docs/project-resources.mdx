[Project](/projects) resources tell agents which code this body of work uses and where to run. Resources stay linked to the project, so there is no need to re-paste repository URLs or local paths into every issue.

Two resource types are supported today:

| Resource | Best for | Where runs happen |
|---|---|---|
| **GitHub repository** | Code shared by the team, with checkouts managed by the runtime | A runtime-managed working directory |
| **Local directory** | An existing checkout, a very large repository, or when you want to inspect local changes directly | The original directory on a specific computer |

## Which setup applies to you

Six combinations cover almost every case. Find your situation in the first column; the sections below explain the pieces.

| | This is your situation | What you bind | Where the work happens | Whose disk, and who clears it | Concurrency | How changes come back to you |
| --- | --- | --- | --- | --- | --- | --- |
| **A** | A local git repository, with or without a remote — **the default** | Local directory · **Direct** | **Your own directory** | Uses no extra space | One run at a time in that directory; later runs queue | Your working copy is edited in place — you `git diff` and revert it yourself |
| **B** | A local git repository that really does need several runs at once | Local directory · **Parallel** | **A working-copy directory beside your repository** — `<repo>.multica-worktrees/<run>` by default | **Your own disk.** Nothing clears it by default; with automatic cleanup on, only copies that are merged, older than N days and free of uncommitted changes | Runs on the same directory run concurrently | The branch is already in your repository, and the working copy stays where you can open it |
| **C** | A plain local folder with no Git at all | Local directory · **Direct** | **Your own directory** | Uses no extra space | One run at a time; later runs queue | Edited in place — no diff, and **no undo** |
| **D** | One directory holding several repositories or several separate bodies of work | Local directory · **Shared** | **Your own directory**, unlocked | Uses no extra space | Concurrent, but nothing is locked, so two runs can step on each other | Edited in place |
| **E** | A cloud project, or this computer has no copy of the code | GitHub repository | A checkout in the Multica workspace | Multica's disk, reclaimed by the normal cleanup cycle | Concurrent by nature | A branch pushed to the remote |
| **F** | Nothing bound — questions and conversation only | Nothing | **One shared session folder** (per conversation, not one folder per run) | Multica's disk, and it stays small | — | Artifacts stay in this conversation's folder under the shared folder |

## How resources enter a run

When an agent works an issue inside the project, Multica adds the project name, project description, and resource list to the run's context, and writes the resource list to `.multica/project/resources.json` — either in the working directory or in the daemon's own per-run folder, depending on where the run happens. See "What gets written during a run" below.

The workspace's linked repository list is always included in the run context. Repositories linked to the project additionally specify the code and default ref this body of work uses.

A local directory only applies to the daemon it is bound to, and it beats a repository. When the computer claiming a run has a local directory for the project, that directory is where the run works — whether or not the project also names a GitHub repository. A repository is used only when no local directory on that machine holds the project's code, and a missing or unusable directory is reported as such rather than quietly replaced by a fresh clone. Other computers keep using the project's GitHub repositories or the workspace repositories.

## Add a GitHub repository

Open the project and choose "Add resource" under **Resources**. Pick a repository already linked to the workspace, or paste a Git URL. Workspace repositories are managed in **Settings → Repositories**; once GitHub is connected, the same page offers **Pick from GitHub** to import repositories the App is authorized for.

Repositories are not limited to GitHub: any Git URL the runtime can reach works as a repository resource. Self-hosted Multica can also connect self-hosted Forgejo, Gitea, or GitLab under **Settings → Integrations → Git hosting**; see [Self-hosted Git hosting](/vcs-integration).

When creating a project, you can also pick repositories directly under **Repos**. One project can link multiple GitHub repositories.

A resource's `ref` sets the branch, tag, or commit that later checkouts use by default. `default_branch_hint` only gives the agent a default-branch hint and does not force a branch switch.

## Add a local directory

The UI for adding a local directory is Desktop-only, because browsers cannot pick folders on your computer.

<Callout type="info">
**A local directory is the default way to give a project code, not an escape hatch.** When the project has a local directory on the computer claiming a run, that is what the run uses; a repository is the fallback for machines that hold no copy of the code.

The folder does not have to be a Git repository. See "Create a local Git repository, or not" below for what you give up when it is not.
</Callout>


1. Make sure Desktop's local daemon is online.
2. Open the project's **Resources**, or the **Local directory** tab of the create-project dialog — the same choice is available before the project exists.
3. Choose "Add local directory", then pick the folder to use.
4. Pick how runs should use it — **Direct**, **Parallel** or **Shared**, described under "How runs share the directory". A new directory always starts on **Direct**: runs happen in the folder you just picked, which costs no extra disk. **Parallel** is an explicit choice because it makes a full working copy per run on your own drive; the dialog names the folder those copies land in before you pick it. Change it right there, or later from **Resources** with the pencil next to the directory.

A directory linked earlier keeps the mode it was saved with — an existing setup is never switched under you.

The directory must be an absolute path, must already exist, and must be readable and writable by the current daemon. These paths are rejected: system roots and drive roots (`/`, `C:\`), home directories themselves and the parents of home directories (such as `/Users`, `/home`, `/root`), and system directories such as `/etc`, `/var`, `/tmp`, `/usr`, and `/opt`. If the chosen path is a symlink, it is resolved to its real path first and validated again by the same rules; the serial lock also applies to the real path.

A project can link **several** local directories on one computer — four unrelated plain folders, or a repository plus a separate docs checkout. What it cannot link twice is the same directory (matched on its resolved real path, so a symlink and its target count as one) or a second checkout of a repository it already has on that computer. Different computers can each link their own directories for the same project.

**One run writes one directory.** Which one follows a two-step rule, computed once on the server and handed to both the runtime and the UI: if the task names a resource explicitly, that resource is used, or the run fails saying why it cannot be; otherwise the run takes **the first local directory for that computer in the list**. The first entry is therefore this machine's default working directory — drag the list, or use the move controls on that computer's directories, to change it. The remaining directories are handed to the agent read-only and named in its brief, so it can read them without treating them as a second place to work.

### Create a local Git repository, or not

A plain folder works as a local directory: bind it and the agent edits it in place, with no Git involved at all. When you add such a folder, Desktop offers to create a local Git repository inside it — and that offer has **nothing to do with GitHub**: a repository created here records changes on this computer and uploads nothing. You can skip it, and the row keeps a "no version control" badge.

What skipping costs you is any record of what happened: there is no `git diff`, no branch to fall back on, and no way to restore a file the agent overwrote. For a folder whose contents you care about, creating the local repository is the cheap insurance.

<Callout type="warning">
In the default `in_place` mode a local directory is not an isolated environment: the agent directly sees and modifies your current branch and uncommitted files, and Multica does not automatically switch branches, stash, commit, push, or open PRs. Worktree mode changes this — see "How runs share the directory" below.
</Callout>

## How runs share the directory

A local directory has three execution modes, set per resource with `execution_mode`. Desktop labels them **Direct**, **Parallel** and **Shared**; the API, the CLI and the rest of this page use the identifiers.

Direct and Parallel are the two that matter for an ordinary repository; the trade-off, before the detail:

| | Direct (`in_place`) — the default | Parallel (`worktree`) |
| --- | --- | --- |
| Disk | Uses no extra space | A full working copy per run, plus that copy's own dependencies, on your project's disk |
| Concurrency | One run at a time in the directory; later runs queue | Any number of runs on the same directory |
| The scene after a failure | Your own directory — the agent edits your working copy as it works, and what it leaves is right where you already are | The working copy beside your repository, which you can open; your own working copy is never touched |
| Who clears it | There is nothing to clear | You do, by default; automatic cleanup is opt-in and removes only merged, clean copies |
| Risk | The agent and your editor write to the same tree | The runs are isolated from each other |

**Direct is the default**, and it is the cheap one: no extra disk and nothing to clean up. Parallel is for a directory that genuinely carries several tasks at once — it buys concurrency with disk on your own machine, and a working copy you are responsible for clearing.

### `in_place` (default) — "Direct"

The agent works directly in your directory, and runs execute one at a time. When two runs use the same real directory, the later one enters `waiting_local_directory` and continues after the earlier one releases the directory. Two paths that reach the same directory through different symlinks serialize the same way.

Waiting does not modify the directory. A waiting run can be cancelled; otherwise it waits until the directory becomes available.

### `worktree` — "Parallel"

Each run gets its own [git worktree](https://git-scm.com/docs/git-worktree) of your repo, created **next to your repository on your own drive** — `<repo>.multica-worktrees/<run>` by default. **Runs on the same directory run concurrently — none of them wait**, and none of them write to your working copy.

The copies sit beside the repository rather than inside it, so they never appear in your own `git status` and you do not have to add anything to `.gitignore`. They are on your disk rather than in Multica's workspace for one reason: when a run fails, that copy is the only record of how far it got, and it should not disappear on a cleanup schedule you never agreed to. The cost is that the space is yours — see "Clearing out working copies" below.

Requires the directory to be a git repository with at least one commit. If it is not, runs fail with an explicit error rather than quietly falling back to serial execution. The runtime on that machine must also implement the mode. It declares that when it connects, and Multica gates on the declaration rather than on a version number — a development build can carry a version string that looks new enough while having none of the implementation. The declaration is checked twice: saving the resource is refused, with a hint to update the app on that machine, while its runtime does not declare the capability; and each run is checked again against the runtime that actually claims it — so a machine downgraded after the resource was saved has its runs cancelled with a reason instead of silently running them in place. Asking for `worktree` is asking for isolation; editing your working copy instead is never the fallback.

What the agent sees, and what you get back:

- **The agent starts from what you see, not from `HEAD`.** Your uncommitted edits and your untracked files are replayed into the worktree, so the agent is not reviewing code you no longer have. Your own working copy, index, and stash list are never touched. If that state cannot be reproduced faithfully — including when there is more untracked content than the replay covers (2000 files / 200 MiB) — the run fails instead of starting from a tree you would not recognise. The usual fix is to gitignore or clean up build output that is not already ignored.
- **The result is a branch in your repo**, one per issue rather than one per run: `agent/<agent>/<issue>` (a chat gets `agent/<agent>/chat-<session>`). The run's **Run details** panel shows the branch name (and lets you copy it); you can also find it with `git branch`. Review it with `git log` / `git diff`, and merge or cherry-pick it yourself. Multica never merges it for you. A run that failed partway still reports its branch, because it still committed whatever the agent had produced.
- **A follow-up continues where the last run stopped.** The next comment on the same issue checks that branch out again, so the agent is standing on the work it just delivered instead of starting from `HEAD` with its own changes stranded on another branch. Only what you changed in your own directory since the last run is replayed on top — the branch already carries the rest. Merge the branch and the next run starts from your `HEAD` again. If two runs on one issue overlap, the second one forks from the first's work onto `agent/<agent>/<issue>-<task>`, because git allows one worktree per branch.
- **If your edits collide with the agent's, the agent resolves them.** When you rewrite the same lines the agent rewrote, git cannot decide which version wins, so the run starts on a conflicted worktree and is told to finish the merge before anything else — `git status` in that worktree lists the unmerged paths. A run that leaves any file unmerged delivers nothing: it fails, keeps the worktree, and the next run offers the same edits again, so your change is never quietly dropped.
- **Only branches Multica owns are continued.** Continuing a branch is decided by an ownership record, not by its name: the record names the conversation, and it names the commit the branch was left at. A branch you created yourself that happens to be called `agent/<agent>/<issue>` is never checked out, appended to, or read as a previous run — and neither is one that no longer contains the recorded commit, so deleting Multica's branch and making your own under that name, or force-moving it onto other history, is safe. In those cases the run takes `agent/<agent>/<issue>-<id>` instead. Committing on top of a delivered branch is the normal case and keeps it continuing — your commit is simply there in the next run. Every branch also starts with a baseline commit of its own, marking the tree the first run began from — that commit is what identifies the branch later, and `git diff <baseline>..<branch>` is exactly the agent's work. A run that could not record its branch — it failed before finishing, the record could not be written, or it reset its worktree past the commit that carried your edits into the branch — reports failure and keeps its worktree, and later runs start a new branch rather than continuing one they cannot prove is theirs.
- **Nothing is silently dropped.** Anything the agent leaves uncommitted is committed to that branch before the worktree is removed, including when the run fails partway. In the rare case that commit itself cannot be made — for example a repo with `commit.gpgSign` and no signing key available to the runtime — the worktree is deliberately kept instead of removed, the run is reported as failed, and `git worktree list` in your repo points at the directory holding the work.
- **A run that changes nothing leaves nothing behind.** Its branch is deleted rather than left as an empty entry in `git branch` — unless it is the issue's branch carrying earlier runs' work, which always survives.

Two things persist in your repo: the branch, and one hidden ref per branch under `refs/multica/local-state/` recording who owns it and what your directory looked like when it was last continued. The hidden refs never appear in `git branch`; list them with `git for-each-ref refs/multica`. Multica deletes each one with its branch, and drops any whose branch you deleted yourself the next time a run starts on that repo — or you can remove them at once with `git for-each-ref --format='%(refname)' refs/multica | xargs -n1 git update-ref -d`.

### `shared` — "Shared"

Runs execute at the same time in your directory with **no lock at all**. Shared mode is for a directory that holds several repositories or several separate bodies of work, where each task isolates itself with its own per-repo worktrees rather than relying on Multica to serialize the folder. Nothing is copied and nothing waits; nothing is locked either, so two runs that do touch the same tree can step on each other. Choose it only when the work inside that directory is genuinely independent. Unlike Parallel, it needs no git repository and no branch hand-back — that part is your own convention.

### Clearing out working copies

A run that finishes cleanly removes its own working copy. One that survives is one a run could **not** finish — an unresolved merge, a commit that failed, a machine that went down — and it stays on disk on purpose: it is the only place that run's state can still be inspected.

Automatic cleanup of those leftovers is a setting on the computer, not on the project, because disk is a property of the computer. It lives in Desktop's daemon settings and is **off by default**. The list of copies and what would happen to each is shown whether the switch is on or off, so you can read the policy's verdict before agreeing to it.

With the switch on, a copy is removed only when **all** of these hold:

1. Multica created it — a worktree you made with `git worktree add` is never touched;
2. no run is using it;
3. its last run finished longer ago than the window you set (14 days by default);
4. `git status --porcelain` in it is empty — files your `.gitignore` covers, such as `node_modules`, do not count;
5. its work is already in the trunk branch — either the branch is contained in trunk, or its changes were squashed into it. A squash merge rewrites the work as a new commit, so the branch itself is never an ancestor of trunk; comparing content rather than ancestry is what makes this rule reachable at all in a squash-merge repository. "The remote branch is gone" and "the pull request is merged" are deliberately *not* accepted: the first cannot tell a merged branch from one that was never pushed, and the second would make cleaning your own disk depend on a network and on GitHub.

Any one of those failing keeps the copy, and the settings screen says which one. Rule 4 is the important one: a merged branch says nothing about what is still sitting in the directory uncommitted, and that is exactly what a failed run leaves behind. Removal always goes through `git worktree remove`, so your repository is never left with a stale `.git/worktrees` entry that would block that name later.

You can also clear a single copy from that list. That says *which* copy, not "ignore the rules" — the same five conditions are re-checked against the directory as it is at that moment.

<Callout type="warn">
**Self-hosted operators:** isolation for this mode is enforced by the server (at save time and again when a runtime claims each run), so a runtime downgraded at any point is caught. The combination that is *not* caught is rolling the server back to a build that predates this feature while runtimes that do not implement the mode are still connected — an old server has no gate, and such a runtime ignores `execution_mode` and would execute the run in place. Do not roll the server back past this release while `worktree` resources exist unless every runtime on those machines is up to date.
</Callout>

<Callout type="info">
Worktree mode covers git repositories. A plain non-git directory still runs serially — that is what `in_place` is for.
</Callout>

## When nothing is bound: the shared session folder

A run with no local directory on its machine and no repository has no code to work in, only somewhere to leave files. It does not get a fresh task directory each time: every turn of a conversation uses one folder, so twenty questions in one thread do not leave twenty folders behind.

The folder is on the computer running the agent, under the daemon's workspaces root, as `.sessions/<workspace-id>/sessions/<conversation-id>`. The workspaces root defaults to `~/multica_workspaces` (`~/multica_workspaces_<profile>` for a named profile) and can be moved with `MULTICA_WORKSPACES_ROOT`.

This folder is Multica's, so it is cleaned automatically: **on by default**, unlike the parallel working copies on your own drive. A conversation's folder is removed only when Multica created it, no run is using it, and it has been idle past the retention window (14 days by default). Desktop's daemon settings show the folder, its size, and each conversation with the reason it would be kept or cleared; you can also clear one conversation there. The scan never leaves that root: a directory of yours, and a working copy beside a repository, are never candidates.

## When the server cannot place a run

Which directory a run writes is decided once, on the server, before a runtime claims the run — and the runtime verifies that decision instead of choosing again. When no answer can be worked out, the run fails with a code rather than falling back to another directory or to a fresh remote checkout: `daemon_cannot_run_mode`, `unknown_execution_mode`, `malformed_resource`, `pinned_resource_not_found`, `pinned_resource_other_machine`, `pinned_resource_unusable`. Each code, with the next step for it, is listed under [Troubleshooting](/troubleshooting#a-run-fails-with-a-code-source-error).

Older runtimes are unaffected. The server narrows the resource list to what the claiming runtime declared it can handle, so a runtime that predates multiple local directories or the new working-copy location receives exactly the resources it did before — **no upgrade is required**, and its runs behave as they always have.

## What gets written during a run

Beyond the code changes the agent makes, the runtime may write into the working directory the instruction files the current AI coding tool needs, plus `.multica/project/resources.json`. Multica removes its own files again when the run ends, so a Direct run hands your folder back as it found it apart from the agent's changes; a Parallel run never writes into your folder at all, and a Shared run keeps Multica's files out of it.

Multica never deletes a linked local directory when cleaning up run environments. The agent's changes to the directory are the same kind of changes as running an AI coding tool in your terminal yourself, and need the same review.

## Manage resources with the CLI

```bash
# Link a repository when creating a project
multica project create \
  --title "Agent UX" \
  --repo https://github.com/multica-ai/multica

# List and add resources
multica project resource list <project-id>
multica project resource add <project-id> \
  --type github_repo \
  --url https://github.com/multica-ai/multica \
  --ref main

# Link a local directory on a specific daemon
multica project resource add <project-id> \
  --type local_directory \
  --local-path /absolute/path/to/repo \
  --daemon-id <daemon-id>

# Link a local git repo and let runs execute concurrently in their own worktrees
multica project resource add <project-id> \
  --type local_directory \
  --local-path /absolute/path/to/repo \
  --daemon-id <daemon-id> \
  --execution-mode worktree

# Switch an existing local directory between modes
multica project resource update <project-id> <resource-id> --execution-mode worktree
multica project resource update <project-id> <resource-id> --execution-mode in_place

# Remove a resource
multica project resource remove <project-id> <resource-id>
```

Resource changes affect runs created afterwards; they do not rewrite records of runs that already ended.
